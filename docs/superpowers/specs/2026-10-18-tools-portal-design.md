# tools.nasekomuspro.ru — инструменты для коллег со входом и правами

Дата: 2026-10-18. Статус: проект, ждёт утверждения пользователя.

## Зачем

Сейчас сайтом с инструментами для манифестов (em.nasekomuspro.ru и GitHub Pages) пользуется только жена пользователя. Коллеги на сайт не заходят: иногда она делает их часть работы сама. Нужен отдельный сайт, где коллеги работают сами, но каждый видит только выданные ему инструменты. Пользователь не хочет показывать всем всё.

Особой секретности нет: репозиторий `nasekomus-cloud/manifest-tools` публичный, старый сайт открыт всем, и так и остаётся (решение пользователя). Цель — **продуманный и надёжный рабочий инструмент для коллег** с учётом того, кто что может и кто что делал. Это не защита наработки.

## Цели

- Вход по почте и паролю. Без входа сайт не отдаёт ни одной страницы инструмента, даже по прямой ссылке.
- Администраторы (пользователь и жена, оба с полными правами) приглашают коллег и галочками выдают им инструменты.
- Коллега сам задаёт себе пароль по ссылке-приглашению.
- Каждый инструмент работает так же, как на старом сайте, с тем же полным результатом на экране: плитки итогов, расхождения по категориям, предупреждения, таблицы дашбордов, кнопки скачивания.
- Инструкция к каждому инструменту: что загрузить, что получится, пример файла.
- Журнал: кто, когда, каким инструментом, с какими файлами (только имена) и с каким итогом.
- «Запросить доступ» к закрытому инструменту.
- Новое оформление «Глубина» (см. ниже).

## Не цели

- Хранить файлы манифестов на сервере. Файлы по-прежнему обрабатываются в браузере и никуда не отправляются. Сервер только пускает людей, отдаёт страницы и пишет журнал.
- Менять старый сайт. em.nasekomuspro.ru и GitHub Pages остаются как есть, со своим оформлением «Лоция».
- Редактор инструкций или справочников в админке. Инструкции пишутся в коде (решение пользователя: «напиши сам, они же простые»).
- Наборы прав или роли кроме «администратор / коллега». Права выдаются поштучно.
- Платные почтовые сервисы (Unisender Go и подобные отклонены пользователем).

## Анти-цели (провал, даже если «работает»)

- Вторая копия логики инструментов (`core.js`, `lib/`). Исправление в сверке должно попадать на оба сайта сразу.
- Сайт, которым нельзя пользоваться без почты. Пока почта не работает, людей всё равно нужно уметь пускать.
- Любое изменение поведения старого сайта.
- Тяжёлый сервер, который не помещается на текущий VPS.

Текст крупный и контрастный: на тёмном фоне мелкий читается хуже. Макеты — `.superpowers/brainstorm/41798-1792325312/content/g-export-import.html` (вариант G1) и `g-results.html`.

## Как устроено (мои решения — проверьте)

### Одна кодовая база, два оформления

Новый сайт живёт в том же репозитории, в каталоге `portal/`. Страницы инструментов (`merge/`, `dg-check/` и т. д.) и `lib/` он **отдаёт те же самые файлы**, без копий. Подменяются только общие файлы оформления:

| Путь, который запрашивает страница | Старый сайт | Новый сайт |
|---|---|---|
| `/assets/style.css` | `assets/style.css` | `portal/web/style.css` («Глубина») |
| `/assets/shell.js` | `assets/shell.js` | `portal/web/shell.js` |
| `/tools.js` | `tools.js` | генерируется сервером для текущего человека (см. ниже) |
| `/` и `/index.html` | `index.html` | главная портала |
| `/assets/fonts.css` | тот же файл | тот же файл |

Новый `portal/web/shell.js` выставляет **тот же** `window.Shell` с тем же поведением, что и старый (`plural`, `setStep`, `setAction`, `setResultShown` с правилом «первая видимая кнопка главная», `formatSize`, `toolNumber`, `remember`, глушение `drop` мимо зоны). Только рисует он верхнюю полосу и путь вместо боковой панели: элемент `#app-side` остаётся в разметке страниц и становится верхней полосой. `portal/web/style.css` обязан покрыть все классы, которые используют страницы инструментов (список в `CLAUDE.md`, раздел про `assets/style.css`: `.steps`, `.action-bar`, `.result__head`, `.stat`, `.data-table`, `.dropzone`, `.file-list`, `.btn`, `.btn--secondary`, `.switch`, `.error-message`, `.warning-message`, `.dashboard-block`, `.port-bar`, `.field-grid`, `.field`, `.dashboard-row--empty` и т. д.). При печати (`@media print`) страница светлая, как старая: тёмный фон на бумаге не нужен, таблицы должны читаться.

Итог: `app.js`, `core.js` и `lib/` не меняются ради нового сайта. Правка инструмента сразу попадает на оба сайта после деплоя каждого.

### Сервер

- Node.js 22 из apt. Встроенные модули: `node:http`, `node:sqlite`, `node:crypto` (`scrypt` для паролей). Зависимостей — минимум; SMTP-клиент (например, `nodemailer`) — только если удобнее, чем свой.
- Слушает `127.0.0.1:<порт>`. Перед ним nginx-vhost `tools.nasekomuspro.ru` с сертификатом certbot, всё проксируется в Node. Запускается systemd-юнитом с `Restart=always` и `enable`, чтобы пережить ночную перезагрузку.
- Одна база SQLite: `/var/lib/manifest-portal/portal.db`. Таблицы: люди, права (человек × инструмент), ссылки-приглашения и сбросы, сессии, журнал, запросы доступа.
- Ответы с `Cache-Control: no-store`, как на em: тогда проблема `?v=` новому сайту не грозит.
- Секреты (настройки SMTP) — в env-файле на сервере, не в репозитории: репозиторий публичный.

### Права

- Ключ права — **каталог инструмента** из `href` в `tools.js` (`merge`, `order-check`, `grand-total`, `grand-total-import`, …). У «Разделить коносаменты» две записи, но один `href`, значит и право одно. У «Итогового отчёта» для экспорта и импорта разные страницы, значит и права разные.
- Любой запрос к `/<каталог>/...` (без учёта `?v=…`) проверяется: нет сессии — перенаправление на `/login?next=…`; нет права — страница «Нет доступа» в новом оформлении с кнопкой «Запросить доступ». Общие `lib/`, `assets/`, `tools.js` отдаются любому вошедшему.
- `/tools.js` сервер собирает из настоящего `tools.js` и добавляет каждой записи признак `allowed`. Главная и полоса рисуют закрытые инструменты пунктиром.
- Новый инструмент, добавленный в `tools.js`, появляется на новом сайте сам и у коллег по умолчанию закрыт. У администраторов открыто всё.

### Вход, приглашения, пароли

- Первого администратора создаёт команда на сервере (например, `node portal/server/cli.js add-admin <почта> <имя>`). Она печатает ссылку-приглашение.
- Приглашение: администратор вводит почту, имя и отмечает инструменты. Сайт создаёт ссылку `/invite/<токен>`, действует 7 дней. По ссылке человек задаёт пароль (не короче 8 символов, дважды) и сразу оказывается внутри.
- Сброс пароля: в админке «Новая ссылка для входа» (`/reset/<токен>`, действует 24 часа). На странице входа «Забыли пароль?»: если SMTP настроен, письмо уходит само; если нет, у администраторов появляется запрос «<имя> не может войти», а человеку показывается «Мы передали администратору».
- Сессия: случайный токен в cookie `HttpOnly; Secure; SameSite=Lax`, **бессрочная** (решение пользователя): на сервере срока нет, человек остаётся внутри, пока сам не выйдет, пока его не отключат или пока не сменится пароль. Браузеры не держат cookie дольше примерно 400 дней (Chrome), поэтому при каждом заходе cookie перевыпускается с `Max-Age` на 400 дней — для человека это и есть «бесконечно». Выход, отключение человека и смена пароля гасят его сессии. Изменяющие запросы проверяют `Origin`.
- Защита от перебора: ограничение попыток входа (порядка 10 за 15 минут на почту и на IP).
- Человек может сам сменить пароль из меню под своим именем.

### Журнал

- Запись делается автоматически, **без правок `app.js`**. Новый `Shell.setResultShown(true)` вызывается на каждой странице в момент, когда результат показан. В этот момент он отправляет на сервер инструмент, имена файлов (из `.file-list`) и итог (подписи и числа плиток `.stat` из `.result__head`, например «455 строк проверено · 7 с расхождениями»).
- Скачивания по желанию тоже пишутся (клик по кнопке в `.result__actions`).
- Отправка в журнал «выстрелил и забыл»: если сервер не ответил, инструмент работает дальше как ни в чём не бывало, ошибок человеку не показываем.
- Коллега видит только свои записи (на главной последние, на странице «Журнал» все). Администраторы видят всех, с фильтром по человеку и инструменту.
- Хранить год, старое удалять. Записи маленькие, диск это выдержит.

### Запрос доступа

- Кнопка «Запросить доступ» создаёт запрос. У администраторов в полосе появляется счётчик, на странице запросов — «Выдать» (одна кнопка ставит право) или «Отклонить». Если SMTP настроен, администраторам уходит письмо.
- Повторный запрос того же инструмента, пока первый не разобран, не плодит новых записей.

### Админка (только для администраторов)

- «Люди»: список (имя, почта, состояние: приглашён / активен / отключён, последний вход), «Пригласить», для каждого — галочки инструментов по вкладкам «Экспорт / Импорт», «Новая ссылка для входа», «Отключить» / «Включить». Администратора нельзя лишить прав из интерфейса, и последнего администратора нельзя отключить.
- «Журнал» всех.
- «Запросы».

### Инструкции к инструментам

- Пишу сам, по коду и `CLAUDE.md`, коротко: что загрузить, что получится, на что обратить внимание. Лежат в `portal/help/<каталог>.md` (или одном JS-файле — на усмотрение исполнителя). Открываются по ссылке «Как это работает» на странице инструмента.
- **Примеры файлов только синтетические.** Генерируются скриптом с выдуманными судами, контейнерами и весами, по образцу тестовых данных. Реальные файлы заказчиков в примеры не попадают никогда.

### Деплой и старый сайт

- `./deploy-tools.sh`: rsync репозитория в `/opt/manifest-portal` на `vps1` (без `.git`, тестов, `node_modules`, `.autopilot`, `.claude`, `.superpowers`), перезапуск systemd-юнита. Первичная установка (nodejs из apt, пользователь сервиса, каталог базы, vhost, certbot) — отдельный разовый шаг, расписанный в плане.
- `deploy-em.sh` дополнить исключением `portal/` и `docs/`: старому сайту они не нужны. Это единственная правка, которая касается старого сайта, на его поведение она не влияет.
- Резервная копия базы — раз в сутки копия файла рядом, хранить 7 штук.
- После добавления vhost проверить, что `default_server` не перехвачен (урок из `CLAUDE.md`): `00-catchall` должен остаться первым.

### Тесты

- Серверная логика под `node --test` в общем `npm test`: права по пути, жизнь токенов, хеширование паролей, ограничение попыток, сборка `tools.js` с `allowed`, разбор итога для журнала.
- Ручная проверка в браузере: каждая из страниц инструментов в новом оформлении на реальных файлах (результат на экране, скачивание, печать).
