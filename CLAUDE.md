# Инструменты для судовых манифестов

Веб-сайт с минимальной автоматизацией для работы с судовыми грузовыми манифестами.

## Команды

| Команда | Что делает |
|---------|------------|
| `npm install` | Установить зависимости (только для тестов — пакет `exceljs`, сайт в проде без npm) |
| `python3 -m http.server` (из корня) → `localhost:8000` | Запустить локально; альтернатива — открыть `index.html` напрямую двойным кликом |
| `npm test` | Прогнать тесты (`node --test`, 82 теста в `lib/`, `merge/`, `dg-check/`, `dashboard/`, `dashboard-departure/`, `bl-split/`, `grand-total/`, `order-check/`) |
| `./deploy.sh` | Обновить копию сайта на собственном VPS пользователя (`root@130.49.213.189`, nginx, `/var/www/manifest-tools`, домен `manifest.nasekomuspro.ru`) — отдельно от GitHub Pages. `rsync --delete` корня репозитория, кроме `.git`/`node_modules`/`.autopilot`/`.claude`/`.agents`/тестов/`CLAUDE.md`/`package*.json`. Пароль SSH вводится вручную при запуске (ключевой доступ на этом сервере сознательно не настраивается) |

## Структура

- `index.html`, `tools.js` — главная страница; `tools.js` — обычный скрипт (`window.TOOLS`, без import/export), список карточек `{title, description, href}`, единственное место для добавления нового инструмента.
- `assets/style.css` — общие стили главной страницы и повторно используемых элементов инструментов (`.dropzone`, `.btn`, `.file-list`, `.error-message`, `.back-link`).
- `lib/manifest-format.js` (+`manifest-format.test.js`) — формат манифеста, экспортирует `validateStructure(workbooks)`, `readVoyageHeader(workbook) -> {vessel, voyage}` (оба `string|null`, поиск по ключевым словам «т/х»/«Рейс» в строке `HEADER_FIRST_ROW`, не по фиксированной колонке) и константы `SHEET_NAME`, `HEADER_FIRST_ROW`, `COLUMN_HEADER_ROW`, `DATA_START_ROW`, `FIRST_COLUMN`, `LAST_COLUMN`.
- `lib/port-breakdown.js` (+`port-breakdown.test.js`) — общая логика подсчёта весов для трёх инструментов (оба дашборда и итоговый PDF-отчёт): `buildPortBreakdownDashboard(workbooks, {portKeyword, portLabel}) -> {ok:true, perFile, combined} | {ok:false, error}` — разбивка по порту и типу; `buildManifestTotals(workbooks) -> {ok:true, byType, grandTotal, billsOfLading} | {ok:false, error}` — разбивка только по типу контейнера (без порта), плюс число уникальных коносаментов. Владеет поиском колонок, нормализацией порта/типа/контейнера, дедупликацией по номеру контейнера, пропуском строк без контейнера — вся логика, которая один раз уже ловила реальный баг (см. ниже), живёт в одном месте, а не в трёх копиях.
- `merge/index.html`, `merge/app.js`, `merge/core.js` (+`core.test.js`) — инструмент склейки: `core.js` экспортирует `mergeManifests(workbooks, {renumber}) -> {resultWorkbook, summary}`, `app.js` — DOM (выбор файлов, drag-and-drop порядка, скачивание).
- `dg-check/index.html`, `dg-check/app.js`, `dg-check/core.js` (+`core.test.js`) — сверка опасных грузов: `core.js` экспортирует `crossCheckDangerousGoods(combinedWb, dgWb) -> {ok, resultWorkbook, summary} | {ok:false, error}`.
- `dashboard/index.html`, `dashboard/app.js`, `dashboard/core.js` (+`core.test.js`) — дашборд по портам **назначения**: `core.js` — трёхстрочная обёртка над `buildPortBreakdownDashboard` с `portKeyword: 'назначения'`, экспортирует тот же `buildPortDashboard(workbooks) -> {ok:true, perFile, combined} | {ok:false, error}`. `app.js` — DOM (загрузка файлов, рендер таблиц с полосой относительного веса по порту, сборка и скачивание Excel-отчёта с листом на файл + листом «Итого»).
- `dashboard-departure/index.html`, `dashboard-departure/app.js`, `dashboard-departure/core.js` (+`core.test.js`) — тот же инструмент, но по портам **отправления**: `core.js` — та же обёртка с `portKeyword: 'отправления'`. `app.js` — копия `dashboard/app.js` (другие подписи колонок/файла), это осознанное дублирование DOM-слоя ради простоты — вся логика, которую стоило не дублировать, уже вынесена в `lib/port-breakdown.js`.
- `core.js` во всех Excel-инструментах не импортирует ExcelJS сам — принимает готовые `ExcelJS.Workbook` снаружи (в браузере от глобального `ExcelJS`, в тестах от `import('exceljs')) — этим и открыт путь тестировать их в Node.
- `bl-split/index.html`, `bl-split/app.js`, `bl-split/core.js` (+`core.test.js`) — разделение PDF с несколькими коносаментами на отдельные файлы по номеру, архивом zip: `core.js` экспортирует `extractBillGroups(pageTexts) -> {ok:true, groups, leadingPages, warnings} | {ok:false, error}` — чистая функция от уже извлечённого текста страниц (`string[]`), без единой PDF-библиотеки, поэтому тестируется в Node без установки чего-либо тяжёлого. `app.js` — три CDN-библиотеки: `pdf.js` (извлечь текст каждой страницы), `pdf-lib` (нарезать страницы по группам, которые вернул `core.js`), `JSZip` (собрать архив). Единственный инструмент сайта не про Excel-манифесты.
- `grand-total/index.html`, `grand-total/app.js`, `grand-total/core.js` (+`core.test.js`) — итоговый отчёт «Grand Total» по манифесту: разбивка по типам контейнеров плюс общий итог, двумя кнопками — PDF и Excel (второе не замена, а вдобавок). `core.js` — трёхстрочная обёртка: `buildGrandTotalData(workbooks) -> {ok:true, vessel, voyage, byType, grandTotal, billsOfLading} | {ok:false, error}` вызывает `buildManifestTotals` (веса) и `readVoyageHeader` (шапка). `app.js` — DOM, три поля ручного ввода (позывной/дата прибытия/терминал — в манифесте их нет ни в каком виде); сборка PDF через `pdf-lib` + `@pdf-lib/fontkit` (см. «Подводные камни» — почему не `StandardFonts`), сборка книги — через уже подключённый `ExcelJS`. Ширина колонок и там, и там — по самому широкому содержимому колонки (`computeColumnWidths`/`computeExcelColumnWidths`), не константой; линии таблицы в PDF — только под шапкой колонок и вокруг строки `TOTAL:`, между строками данных линий нет — так же, как в приложенном пользователем образце (`.autopilot/2026-09-06-manifest-pdf-report/reference.md`).
- `order-check/index.html`, `order-check/app.js`, `order-check/core.js` (+`core.test.js`) — сверка сводного файла с поручениями на погрузку: `core.js` экспортирует `crossCheckOrders(combinedWb, orderEntries) -> {ok:true, resultWorkbook, summary, warnings} | {ok:false, error}`, где `orderEntries: Array<{fileName, workbook}>` — сверяет по номеру контейнера вес груза/тары/общий, пломбы, тип контейнера, номер поручения, класс опасного груза (общий вес проверяется как сумма веса груза и веса тары **по поручению**, а не по столбцам свода — иначе расхождение, где сам общий вес в своде перепутан со значением соседней строки при верных весе груза и тары по отдельности, осталось бы незамеченным); дописывает столбец `LAST_COLUMN+1` и красит расходящуюся строку жёлтым через `cloneStyle` — тот же приём, что в `dg-check/core.js`/`merge/core.js` (мутирует и возвращает тот же `combinedWb`, не копию). `app.js` — DOM: два дропзоны (сводный файл — один `.xlsx`; поручения — `.zip` через JSZip 3.10.1 и/или несколько `.xlsx` вперемешку, служебные записи архива `__MACOSX/`/`.DS_Store`/каталоги молча пропускаются), сводка расхождений по категориям, список предупреждений о нечитаемых файлах, скачивание результата. Из общих модулей сайта переиспользует только константы `lib/manifest-format.js` (не сам файл манифеста целиком — поручение отдельный формат, разбирается только внутри `order-check/core.js`).

## Подводные камни

- Формат манифеста зашит в `lib/manifest-format.js` как константы (лист `"Manifest"`, шапка рейса — строки 3–5, заголовки колонок — строка 5, данные с 6-й, диапазон колонок C:Y) — если реальный шаблон манифеста изменится, править только там, все `core.js` переиспользуют эти константы, а не дублируют числа.
- В `dg-check/core.js` колонки и сводного файла, и DG-манифеста ищутся по тексту заголовка, а не по фиксированной букве столбца — раскладка DG-манифеста официально не фиксирована. DG-манифесты — официальные международные документы, заголовки на английском («CNTR No.», «UN No.», «CLS(Sub)»), поэтому у контейнера и класса по два варианта ключевых слов (рус/англ) в `DG_SPECS`; при новых формулировках заголовков — добавлять туда, а не менять номер колонки.
- В `lib/port-breakdown.js` поиск колонок веса — по ключевым словам «груза»/«тары»/«общий», а не «вес» целиком: в реальных файлах-примерах заголовки написаны как «Веc груза»/«Веc тары»/«Общий Веc» с латинской `c` вместо кириллической (проверено побайтово), слово «вес» в них не встречается ни разу. Колонка-порт (назначения/отправления) ищется тем же приёмом — ключевые слова «назначения»/«отправления» не пересекаются, поэтому один и тот же поиск безопасен в обе стороны.
- `normalizePort` в `lib/port-breakdown.js` схлопывает не любые повторные пробелы, а именно пробел перед «(»: один и тот же порт в реальных данных встречается то как «…Port (RUPLP)», то как «…Port(RUPLP)» — отличие в наличии ровно одного пробела, а не в его количестве, поэтому `\s+\(` убирается до общего схлопывания `\s+`.
- В `lib/port-breakdown.js` строка без номера контейнера **не считается данными вообще** — это не только защита от пустых строк-разделителей, а прямое следствие реального файла: под последней строкой данных там стоит ещё одна строка с формулами `СУММ()` по весу (без контейнера, порта и типа), и раньше она проходила фильтр «есть хоть один вес» и удваивала итоговый вес всего файла. Номер контейнера — обязательная шестая колонка (ключевое слово «контейнера»), а не просто поле для показа. `buildManifestTotals` из-за этого же правила явно отказывает ошибкой «Не найдено ни одной строки с контейнером», если после фильтра не осталось ни одной строки данных — без этой проверки отчёт молча показал бы нулевой итог, как будто в манифесте нет груза (найдено при ревью, до выпуска, тестом).
- «Кол-во» в `lib/port-breakdown.js` — число **уникальных** номеров контейнера в группе, не число строк: один физический контейнер с несколькими видами груза в реальных манифестах занимает несколько строк с одним и тем же номером (проверено на реальном файле пользователя — три строки на контейнер `MSKU8627414`, разный вес на каждой строке). Вес при этом суммируется по каждой строке — это разные части груза одного контейнера, а не задвоенные записи. Подробности и как это обнаружилось — `.autopilot/2026-09-06-port-dashboard/spec.md`, раздел D01. Логика была сначала в `dashboard/core.js`, потом вынесена в `lib/port-breakdown.js` при добавлении `dashboard-departure/` — второй копии этого (уже однажды забагованного) кода заводить не стали.
- Чтение `.text` у объединённой ячейки с пустым мастером бросает исключение внутри ExcelJS (`MergeValue.toString` на `null`) — встречается в реальных DG-манифестах с шапками из склеенных пустых ячеек. `cellText()` в `dg-check/core.js` оборачивает это в try/catch — не убирать при рефакторинге.
- Сравнение старого и нового значений в `dg-check/core.js` — не строковое равенство, а сравнение множеств пар «класс|UN» (`parseDangerousGoodsEntries`/`sameDangerousGoods`). Причина: реальная колонка «Опасные грузы» пишется не этим сайтом и использует свои разделители (`;\r` вместо `" / "`) и группировку («IMO 9 UN 3077,3082» вместо двух отдельных записей) — точное сравнение текста давало расхождение почти на каждой строке при одинаковых по сути данных (проверено на реальных файлах пользователя: было 71 «расхождение» вместо 2 настоящих).
- `index.html`/`tools.js` — обычные скрипты без `import/export`, специально ради открытия двойным кликом (`file://`); `merge/app.js` и `dg-check/app.js` — `<script type="module">` и используют `import` из `core.js`/`lib/manifest-format.js`, поэтому эти две страницы требуют http(s) (локальный сервер или GitHub Pages), а не `file://`.
- ExcelJS в браузере — CDN-тег с зафиксированной версией `4.4.0` (в `merge/index.html`, `dg-check/index.html`, `dashboard/index.html`, `dashboard-departure/index.html`, `grand-total/index.html`), в тестах — npm-пакет `exceljs` из `devDependencies`; расхождение версий между ними — источник несовпадений, которые не поймает `npm test`.
- `mergeManifests` копирует колонки `A:Y` целиком (не `C:Y`), потому что в реальных файлах заголовок «№п/п» стоит в колонке **C** (A и B пустые) — колонка `A` в диапазон копирования попадала по историческому предположению, что нумерация там, но проверено на реальном файле пользователя: это не так. Колонка для сквозной нумерации (`renumber`) ищется по заголовку «п/п» тем же `findColumnByKeyword`, что и «контейнер»/«коносамент», с запасным вариантом — колонка A, если заголовок вообще не нашёлся; сама `validateStructure` при этом сверяет только `C5:Y5`, колонки вне этого диапазона в проверку структуры не входят.
- `crossCheckDangerousGoods` мутирует и возвращает тот же объект `combinedWb` (не копию), дописывая столбец `LAST_COLUMN+1` (Z) и заливая жёлтым (`FFFFFF00`) весь диапазон `C:Z` строки при расхождении.
- Перед покраской ячейки стиль клонируется (`cloneStyle`), а не мутируется через `cell.fill = ...` напрямую: ExcelJS при чтении реального файла отдаёт ОДИН объект стиля сразу сотням ячеек с одинаковым оформлением (проверено: 8 уникальных стилей на 2185 ячеек в реальном файле пользователя), и прямая мутация красила жёлтым все ячейки, случайно делящие тот же стиль, — не только расходящуюся строку. Тот же приём (`cloneStyle` перед записью стиля) уже используется в `merge/core.js` — не убирать при рефакторинге ни там, ни здесь.
- Сайт статический (ES-модули, никакой сборки), опубликован на GitHub Pages: https://nasekomus-cloud.github.io/manifest-tools/ — репозиторий `nasekomus-cloud/manifest-tools`, ветка `main`, публикуется автоматически при пуше.
- `mergeManifests` также возвращает `duplicateContainers` — список контейнеров, встретившихся больше одного раза в своде, с номерами строк результата (обычные номера строк Excel, не индекс в списке), отсортированный по первой строке появления; `null`, если колонка «контейнер» не найдена (как и у `uniqueContainers`). Строки для дублей собираются в `Map<нормализованный контейнер, number[]>` во время того же прохода, что и подсчёт уникальных, — отдельного прохода по данным не заводили.
- `mergeManifests` считает `uniqueContainers`/`uniqueBillsOfLading` в сводке — колонки «№ контейнера»/«№ коносамента» ищутся в шапке результата по ключевому слову (`findColumnByKeyword`, тот же приём, что в `dg-check/core.js`), а не по фиксированной букве. Значения нормализуются (`trim().toUpperCase()`) перед добавлением в `Set`, чтобы регистр и пробелы не плодили ложные дубликаты. Если нужный заголовок не найден — поле в сводке `null` (не `0`, чтобы не путать «не нашли колонку» с «нашли, но там пусто»), и `merge/app.js` показывает вместо числа «колонка не найдена».
- В `bl-split/core.js` титульный лист коносамента находится по фразе «INTERNATIONAL BILL OF LADING» в тексте страницы, а не по номеру/позиции — граница между коносаментами (сколько у него страниц-приложений) в реальном файле не постоянна: в примере пользователя (732 страницы, 319 коносаментов) от 2 до 18 страниц на один коносамент. Номер коносамента (`OVP[A-Z0-9_]{6,}`, например «OVPB26Q000717» или «OVPGISKKGD000022B_F») ищется **только на титульном листе**, не по всему диапазону страниц: страницы-приложения содержат свои, более короткие «OVP...»-коды (другое поле — не номер коносамента), которые иначе перепутались бы с настоящим номером (проверено на реальном файле — короткие коды вида «OVP643504» встречаются на приложениях сплошь и рядом).
- В `bl-split/app.js` файл читается через `file.arrayBuffer()` **дважды отдельными вызовами** — один раз для `pdf.js` (извлечь текст), второй раз для `pdf-lib` (нарезать страницы), а не один и тот же буфер передаётся в обе библиотеки: часть сборок `pdf.js` передаёт буфер во внутренний воркер с переносом владения (transferable), после чего он непригоден для повторного чтения. `File.arrayBuffer()` можно звать сколько угодно раз — каждый раз отдаёт свежую независимую копию.
- `pdf.js` в `bl-split/` — версия `3.11.174`, а не последняя: с 4.x пакет на cdnjs распространяется только как ES-модуль (`pdf.min.mjs`, без глобальной переменной), а сайт держит все свои сторонние библиотеки как обычные `<script>`-теги с глобальной переменной (как ExcelJS) — 3.11.174 последняя версия с таким UMD-сборкой (`pdf.min.js` + `pdf.worker.min.js`).
- GitHub Pages отдаёт `.js` с `Cache-Control: max-age=600` — браузер до 10 минут не перечитает изменённый файл даже по обычной перезагрузке страницы (не хардрефрешу). Поэтому все ссылки на свой JS (`<script src="...">`/`<script type="module" src="...">` в `index.html`/`merge/index.html`/`dg-check/index.html`/`dashboard/index.html`/`dashboard-departure/index.html`/`bl-split/index.html`/`grand-total/index.html`, и `import ... from '...core.js?v=...'`/`'...manifest-format.js?v=...'`/`'...port-breakdown.js?v=...'` внутри `app.js`/`core.js`) несут `?v=<YYYYMMDDHHMM>`. **При каждой правке `core.js`/`app.js`/`manifest-format.js`/`port-breakdown.js`/`tools.js` — обновляй это число везде, где встречается**, иначе фикс не долетит до уже открытых вкладок ещё 10 минут (это уже случалось: жена тестировала правки со старым закэшированным JS и ловила старые баги). Правка `lib/manifest-format.js` или `lib/port-breakdown.js` тянет за собой каскад: у них меняется число → у всех `core.js`, что их импортируют, меняется содержимое строки импорта → у их `app.js` меняется строка импорта `core.js` → у их `index.html` меняется `<script src="app.js?v=...">`. Обновлять нужно всю цепочку, а не только сам изменённый файл.
- `grand-total/app.js` рисует PDF не встроенными 14 шрифтами `pdf-lib` (`PDFLib.StandardFonts.Helvetica`) — их WinAnsi-кодировка не содержит кириллицу вовсе, `page.drawText('ВЫГРУЗКА ...')` бросает исключение прямо внутри `pdf-lib` (найдено при ручной проверке в браузере на реальном файле). Вместо этого шрифт (Roboto) грузится с постоянного версионированного URL `fonts.gstatic.com/s/roboto/v51/...ttf` и встраивается через `@pdf-lib/fontkit` (единственная зависимость сайта не с cdnjs — берётся с `cdn.jsdelivr.net`, на cdnjs `fontkit`а нет) с `embedFont(bytes, { subset: true })`. **Не через Google Fonts CSS API с `text=<нужные символы>`** (первая попытка): тот вариант отдаёт уже урезанный на сервере `.woff2`, и с этой же версией `pdf-lib` (`1.17.1`) и `@pdf-lib/fontkit` (`1.1.1`) он либо зависает на `doc.save()` без ошибки и без таймаута, либо — если отключить повторное подрезание (`subset: false`) в обход зависания — даёт неверную раскладку глифов (текст читается как случайный набор символов). Обычный статический `.ttf` с постоянного URL обеих проблем не имеет.
- В Excel-выгрузке `grand-total/app.js` веса — числа с `numFmt` (`#,##0.000" KGS"`), а не готовый текст «8 692 506,220 KGS»: `numFmt`, поставленный на строковую ячейку, в Excel не действует (ячейка остаётся текстом, не числом). Поэтому у Excel-строк — свой источник (`buildExcelRows`), с сырыми `entry.cargoWeight`/`entry.tareWeight`/`entry.totalWeight`, а не общий с PDF и предпросмотром `buildTableRows` (там вес уже отформатирован в текст — то, что нужно для `page.drawText`, но не для числовой ячейки). Ширина колонок Excel-листа при этом всё равно считается по отображаемому тексту (число, прогнанное через тот же `formatWeight`, что и в PDF), а не по длине самого числа — иначе колонка веса окажется у'же, чем нужно для « KGS».
- Заголовки колонок поручения в `order-check/core.js` (`ORDER_HEADERS`, `findOrderColumns`) ищутся точным совпадением текста ячейки (после `trim().toLowerCase()`), не вхождением подстроки — «брутто груза» является подстрокой заголовка «Брутто груза с весом контейнера» в реальном поручении, нестрогий поиск задел бы не ту колонку и веса разошлись бы систематически на вес тары.
- Строки поручения с наименованием груза «поддоны»/«поддон»/«палеты»/«палета»/«паллеты»/«паллета» (`PALLET_CARGO_NAMES` в `order-check/core.js`) исключаются из веса груза контейнера — вес тары упаковки, не содержимого. Сравнение тоже точное (`trim().toLowerCase()` в `Set.has`), не по вхождению: под нестрогое совпадение «поддон» иначе попала бы реальная позиция груза «поддон анализатора ситового» и её вес пропал бы из сверки.
- Сопоставление контейнер↔поручение в `crossCheckOrders` — сперва по паре ключей `` `${номер поручения}::${номер контейнера}` `` (`index`), и только если пары нет — откат на поиск контейнера по одному ключу среди всех поручений (`containerToOrders`), с пометкой «поручение указано неверно». Оба индекса строятся заранее по всем загруженным поручениям, потому что один контейнер в реальных данных может стоять под несколькими поручениями (сборный/групповой контейнер) и первое совпадение — не обязательно то, что записано в своде.
- Соответствие «код ISO → футность» в `crossCheckOrders` не зашито константой, а строится на лету по большинству (`isoFrequency`/`isoToFutnost`): для каждого ISO-кода, встретившегося у сопоставленных контейнеров текущей загрузки, берётся футность, которая чаще всего стоит в своде рядом с этим ISO. Официального справочника ISO→футность на сайте нет ни в одном модуле, а завести его константой означало бы держать её в синхроне с кодами, которых в реальных поручениях могло и не быть.
- Общий вес в `crossCheckOrders` сравнивается не с суммой столбцов «Веc груза»/«Веc тары» самого свода, а с суммой этих же величин, взятых из поручения (тех же, что уже сверяются как вес груза/тары по отдельности) — иначе строка, где общий вес перепутан со значением соседней при сборке свода (реальный случай, найденный на файле пользователя), осталась бы незамеченной, если бы вес груза и тары сами по себе совпали.
- **ExcelJS 4.4.0 умеет прочитать условное форматирование любого типа, но при записи поддерживает только `expression`/`cellIs`/`top10`/`aboveAverage`/`dataBar`/`colorScale`/`iconSet`/`containsText`/`timePeriod`** (см. `node_modules/exceljs/lib/xlsx/xform/sheet/cf/cf-rule-xform.js` — `render()` там `switch` без `default`, для остальных типов просто ничего не пишет). Правило типа `duplicateValues` (подсветка повторов — реально встретилось в файле пользователя, колонка «Футность») в этом случае пишется как пустой `<conditionalFormatting/>` без `<cfRule>` внутри — невалидно по схеме OOXML, Excel при открытии предлагает восстановить/удалить нечитаемое содержимое. Баг библиотеки, воспроизводится даже на чистой загрузке-сохранении без единой собственной правки (`workbook.xlsx.readFile()` → `writeFile()`), пересоздание правила через `addConditionalFormatting()` не помогает — проблема в самом рендере `cfRule`, не в модели. `crossCheckOrders` перед возвратом результата (`dropUnwritableConditionalFormatting`) убирает из `sheet.conditionalFormattings` любые правила не из этого белого списка — сама подсветка дублей при этом теряется, но файл остаётся читаемым, что важнее. Этот же баг актуален для любого другого инструмента сайта, который читает и пересохраняет файл с условным форматированием неподдерживаемого типа (`merge`, `dg-check`, `dashboard`, `dashboard-departure`, `grand-total`) — там защиты пока нет.
