# Инструменты для судовых манифестов

Веб-сайт с минимальной автоматизацией для работы с судовыми грузовыми манифестами.

## Структура

- `tools.js` — обычный скрипт (`window.TOOLS`, без import/export), единственное место для добавления нового инструмента. Запись: `{num, title, navTitle?, description, href, category: 'export' | 'import', output?: 'xlsx' | 'pdf' | 'zip'}` — `num` номер инструмента для разговора с заказчиком («№ 5», просьба пользователя 2026-10-18): закреплён за инструментом, а не вычисляется по порядку — при перестановке записей не меняется, новому инструменту — следующий свободный (сейчас 14); экспорт — 1–7, импорт — 8–13, у обеих записей «Разделить коносаменты» общий № 6; показывают его `shell.js` (панель, крошки, плашка перед `h1.page__title`, начало `<title>`) и главная (маршрут, карточки) через `Shell.toolNumber(tool)`; `title` полное название (карточка, крошки), `navTitle` короткое имя для панели и маршрута (нет — берётся `title`), `href` путь от корня сайта, `output` метка формата результата. **Порядок записей = порядок в боковой панели, в «маршруте» и в карточках главной** (внутри каждой вкладки) — больше порядок нигде не задан, переставить инструменты значит переставить записи. «Разделить коносаменты» стоит двумя записями (`category: 'import'` и `category: 'export'`), обе на один и тот же `href: 'bl-split/index.html'` — второй пункт входа на тот же инструмент, без второй копии кода в `bl-split/`.
- `index.html` — главная («С чего начать»): тот же каркас `.app`, что у инструментов, но без шагов и полосы действия. Два блока `section[data-tab-panel="export"|"import"]`, в каждом — «маршрут» (`ol.route__stops`, обычный порядок работы, `navTitle` + метка `output`) и карточки (`.tool-cards` → `a.tool-card`); оба строит встроенный `<script>` по `window.TOOLS`. Какой блок виден — решает переключатель вкладок `assets/shell.js` (атрибут `hidden` на блоке). CSS-счётчика номеров карточек больше нет.
- `assets/shell.js` — общий каркас «Лоции», обычный скрипт (без import/export, работает и на `file://`, как `tools.js`), выставляет `window.Shell`: `plural(n, one, few, many)` (**только слово, без числа**: `plural(3,'строка','строки','строк') === 'строки'`), `setStep(1|2|3)`, `setAction({info, hint|null})` (текст `#action-info` — с `aria-live`, подсказка `#action-hint` прячется при `null`), `setResultShown(bool)`, `formatSize(bytes)` («840 Б»/«84 КБ»/«12,4 МБ», неразрывный пробел перед единицей), `toolNumber(tool)` («№ 5» по `num`, `''` без номера), `remember(key, elements)` — память полей формы: последние введённые значения (`value`, у флажка/тумблера — `checked`) подставляются при открытии страницы и сохраняются при каждой правке, `localStorage` под `manifest-tools:fields:<key>` по `id` поля, с try/catch; значения ставятся без событий `input`/`change`. Зовут: «Итоговый отчёт» (`grand-total:export`/`grand-total:import` — память раздельная, поле порта там значит разное), склейка (`merge` — тумблер нумерации). **Новое поле ввода на странице — добавлять в её вызов `Shell.remember`** (просьба пользователя 2026-10-15: во всех формах предлагать последнее введённое). Исключение — «Файлы для АРМ»: там своя память по паре «судно|рейс» (см. ниже), не через `remember`. Сам рисует: боковую панель в `#app-side` (бренд, пометку «файлы никуда не отправляются», переключатель «Экспорт / Импорт» — вкладки с клавишами ←/→/Home/End, список инструментов вкладки с `aria-current` у текущего), мобильное меню (кнопка «Инструменты» уже 900px, Escape закрывает), крошки в начале `.app__main` («Вкладка / Название», вкладка — ссылка на главную), номера и ✓ у шагов `#steps`. Корень сайта вычисляет от собственного `src` (`new URL('../', currentScript.src)`) — одинаково на GitHub Pages в подпапке, в корне домена и на `file://`; текущий инструмент — по адресу страницы среди `href` из `tools.js`. Вкладка запоминается в `localStorage` (`manifest-tools:tab`, с try/catch): на странице инструмента открыта вкладка этого инструмента, у «Разделить коносаменты» (он в обеих) — запомненная. Ещё глушит `dragover`/`drop` файла, брошенного мимо `.dropzone`, — иначе браузер открыл бы файл вместо страницы с уже загруженными файлами; на странице для этого ничего делать не нужно.
- Контракт разметки страницы инструмента (то, что читает `shell.js`): `<body class="app">`; первым ребёнком — пустой `<aside class="app__side" id="app-side"></aside>`; `<main class="app__main">`, внутри — `<ol class="steps" id="steps">` с тремя `<li>` голым текстом (подписи шагов, номер дорисует shell), `<div class="action-bar" id="action-bar">` с `<p class="action-bar__info" id="action-info">`, `<span class="action-bar__hint" id="action-hint">` и главной кнопкой запуска (`.btn`, первая в полосе); **на странице ровно один `.result__head`** (в нём `.result__stats` с плитками `.stat` и `.result__actions` с кнопками скачивания). Порядок подключения: `<link>` на `assets/fonts.css`, затем `assets/style.css`; скрипты в конце `<body>` — `tools.js` → `assets/shell.js` → CDN-библиотеки → `<script type="module" src="app.js">`.
- `assets/fonts/` — исходники шрифтов: Onest (интерфейс) и JetBrains Mono (номера, коды, числа) в `.woff2` (Fontsource, переменная насыщенность, подмножества cyrillic + latin) и лицензии `LICENSE-Onest.txt`/`LICENSE-JetBrainsMono.txt` (OFL-1.1). В браузер они идут не отдельными файлами, а через `assets/fonts.css` — четыре `@font-face` с байтами шрифта в `data:`-URI (~135 КБ): страница, открытая двойным кликом (`file://`), не может загрузить шрифт отдельным файлом. `fonts.css` руками не править — при обновлении шрифта пересобрать из `assets/fonts/` (скрипта сборки в репозитории нет). Google Fonts интерфейс сайта не использует (не путать с Roboto для PDF в `grand-total/app.js` — см. «Подводные камни»).
- `assets/style.css` — весь внешний вид «Лоции» (токены `--font-ui`/`--font-mono`, палитра, каркас `.app`/`.app__side`/`.app__main`, `.side__*`, `.crumbs`, `.steps`, `.action-bar`, `.result__head`, `.stat`, `.data-table`, `.dropzone`, `.file-list`, `.btn`/`.btn--secondary`, `.switch`, `.error-message`/`.warning-message`, `.route`, `.tool-card`, `.fmt`, общие `.dashboard-block`/`.port-bar`/`.field-grid`/`.field`). Глобально `[hidden]{display:none!important}` — видимость переключается атрибутом `hidden`.
- Правило «одна пурпурная кнопка»: `Shell.setResultShown(true)` делает главной (без `.btn--secondary`) **первую видимую** (без атрибута `hidden`) `.btn` в `.result__head`, остальные там и кнопку запуска в `#action-bar` — второстепенными; `false` — обратно. Условие видимости понадобилось «Проверить шаблон»: там кнопка «Скачать исправленный шаблон» сама скрыта, если нечего исправить автоматически, и главной должна стать следующая по порядку, а не пропавшая; на страницах без скрытых кнопок результата (`grand-total/`, `merge/` и остальные) поведение не изменилось. Каждая страница зовёт `setResultShown(false)` в своей функции, прячущей результат, и `true`, когда результат показан. Смена набора файлов или параметра, влияющего на результат (например, тумблер нумерации в склейке), прячет готовый результат (`setChanged()` → `hideSummary()` на всех страницах, кроме `bl-split` — там `clearResults()`), чтобы нельзя было скачать устаревший. **Исключение — поля «Данные судна» (позывной/дата прибытия/терминал) в Итоговом отчёте**: они читаются в момент скачивания (`getValidatedManualFields`), поэтому их правка результат не прячет — это намеренно, не «исправлять».
- Плитки `.stat`, строки `.file-list` (имя, число строк или размер, «✕») и перетаскивание файлов в зону строятся в `app.js` каждой страницы копией фрагмента из `merge/app.js` (образец) — принятое на сайте дублирование DOM-слоя, как `dashboard-departure/app.js`. Перестановка строк перетаскиванием есть только в склейке. У двух сверок (`dg-check/app.js`, `order-check/app.js`) строка файла пока построена иначе — общим помощником `renderFileRow`/`fileRow` на два списка (сводный файл + DG-манифест/поручения). «Проверить шаблон» (`template-check/app.js`) — третий вариант: одна зона и один список на оба вида файлов сразу (шаблон и поручения вперемешку), со своей копией `fileRow` (имя как в `order-check/app.js`, код не общий) — какой это файл, показывает `entryMeta` по `entry.status`, выставленному `detectFileKind` при добавлении.
- `lib/manifest-format.js` (+`manifest-format.test.js`) — формат манифеста, экспортирует `validateStructure(workbooks)`, `readVoyageHeader(workbook) -> {vessel, voyage}` (оба `string|null`, поиск по ключевым словам «т/х»/«Рейс» в строке `HEADER_FIRST_ROW`, не по фиксированной колонке), `rowHasData(sheet, rowNumber) -> boolean` (есть ли непустая ячейка в `A:Y`), `countDataRows(workbook) -> number | null` (строки с `rowHasData` от `DATA_START_ROW` до конца листа `"Manifest"`, строка-довесок с `СУММ()` тоже считается; `null` — нет листа) и константы `SHEET_NAME`, `HEADER_FIRST_ROW`, `COLUMN_HEADER_ROW`, `DATA_START_ROW`, `FIRST_COLUMN`, `LAST_COLUMN`, `ROW_FIRST_COLUMN` (= 1, колонка A — первая колонка строки данных). `countDataRows` — ровно то число, что склейка показывает в «Строк» (склейка берёт `rowHasData` и `ROW_FIRST_COLUMN` отсюда, есть тест на совпадение в `merge/core.test.js`); его зовут `app.js` всех страниц, кроме `bl-split` (там PDF), чтобы показать число строк рядом с файлом.
- `lib/port-breakdown.js` (+`port-breakdown.test.js`) — общая логика подсчёта весов для четырёх инструментов (оба дашборда, итоговый PDF-отчёт, склейка манифестов): `buildPortBreakdownDashboard(workbooks, {portKeyword, portLabel, splitEmpty?}) -> {ok:true, perFile, combined} | {ok:false, error}` — разбивка по порту и типу, `splitEmpty` (по умолчанию `false`) дополнительно отделяет порожние контейнеры (вес груза строго 0) от гружёных того же типа в том же порту — своей строкой с `isEmpty: true` в `types[]`, тем же приёмом, что и `buildTypeBreakdown` ниже (см. «Подводные камни»); `buildManifestTotals(workbooks) -> {ok:true, byType, grandTotal, billsOfLading} | {ok:false, error}` — разбивка только по типу контейнера (без порта), плюс число уникальных коносаментов; каждая запись `byType` несёт `isEmpty` безусловно (не через параметр — порожние контейнеры того же типа считаются отдельной строкой всегда). Владеет поиском колонок, нормализацией порта/типа/контейнера, дедупликацией по номеру контейнера, пропуском строк без контейнера — вся логика, которая один раз уже ловила реальный баг (см. ниже), живёт в одном месте, а не в четырёх копиях.
- `lib/loading-order.js` (+`loading-order.test.js`) — формат поручения на погрузку, общий для «Сверить с поручениями» (`order-check`) и «Проверить шаблон» (`template-check`): экспортирует `parseLoadingOrder(workbook) -> {ok:true, order} | {ok:false, error}` (форма `order` — 13 полей шапки, пустая строка при отсутствии подписи, и `containers[]` из 13 полей на контейнер: `containerNumber`, `row`, `owner`, `isoCode`, `sealNumber`, `places`, `goodsCount`, `goodsNames`, `cargoWeight`, `palletWeight`, `tareWeight`, `totalWeight`, `dangerousGoods`) и `PALLET_CARGO_NAMES` (см. «Подводные камни»). Таблица кончается строкой «Дополнительные сведения» (текст ниже не создаёт ложный контейнер), подписи шапки ищутся во всех строках выше строки заголовков таблицы, а не в фиксированном диапазоне — разбор был раньше только в `order-check/core.js`, второй копии теперь не заводят.
- `lib/xlsx-safe-write.js` — обход бага записи условного форматирования ExcelJS 4.4.0 (см. «Подводные камни»), перенесён сюда из `order-check/core.js`: экспортирует `dropUnwritableConditionalFormatting(worksheet) -> void`, меняет лист на месте. Вызывают `order-check/core.js` (`crossCheckOrders`, раз на сводный лист) и `template-check/core.js` (`buildMarkedWorkbook`, по разу на каждый лист книги с пометками).
- `merge/index.html`, `merge/app.js`, `merge/core.js` (+`core.test.js`) — инструмент склейки: `core.js` экспортирует `mergeManifests(workbooks, {renumber}) -> {resultWorkbook, summary}`, где `summary.weightTotals` и `summary.files[i].weight` (оба `{cargoWeight, tareWeight, totalWeight} | null`) считаются через `buildManifestTotals` из исходных `workbooks`, а не из `resultWorkbook` — тот же класс бага, что и «Кол-во» в `lib/port-breakdown.js` ниже (строка-довесок с формулами СУММ() без контейнера иначе задвоила бы вес). Какие строки копировать, решает `rowHasData` из `lib/manifest-format.js` (своей копии в `core.js` больше нет), диапазон копирования начинается с `ROW_FIRST_COLUMN`. `app.js` — DOM и образец для остальных страниц (выбор файлов, число строк у каждого файла через `countDataRows`, drag-and-drop порядка, тумблер сквозной нумерации, скачивание, своя копия `formatWeight` как в `grand-total/app.js`, таблица «Результат» на 5 колонок: Файл/Строк/Вес груза/Вес тары/Общий вес).
- `dg-check/index.html`, `dg-check/app.js`, `dg-check/core.js` (+`core.test.js`) — сверка опасных грузов: `core.js` экспортирует `crossCheckDangerousGoods(combinedWb, dgWb) -> {ok, resultWorkbook, summary} | {ok:false, error}`.
- `dashboard/index.html`, `dashboard/app.js`, `dashboard/core.js` (+`core.test.js`) — «Информация по портам назначения» (вкладка «Экспорт», последняя запись в `tools.js`; каталог и модуль по-прежнему называются `dashboard/` — переименовано только отображаемое название, не путь): `core.js` — трёхстрочная обёртка над `buildPortBreakdownDashboard` с `portKeyword: 'назначения', splitEmpty: true`, экспортирует тот же `buildPortDashboard(workbooks) -> {ok:true, perFile, combined} | {ok:false, error}`. `app.js` — DOM (загрузка файлов, рендер таблиц с полосой относительного веса по порту, строка порожних — подпись `<тип> — порожние` и класс `.dashboard-row--empty`, что на странице, что в Excel), сборка и скачивание Excel-отчёта с листом на файл + листом «Итого», отформатированного для печати (`formatSheetForPrint`: альбомная ориентация, `fitToWidth:1/fitToHeight:0`, `Print_Area`/`Print_Titles` (повтор шапки), рамка и ширины колонок тем же приёмом, что в `bl-registry/app.js`, `numFmt: '#,##0.000'` (`WEIGHT_NUMFMT`) на весах, жирный шрифт на итоговых строках). **Веса везде с тремя знаками после запятой** — на странице (`fmt`: `62 372,400`, приём `formatWeight` из `grand-total/app.js` без « KGS»), в Excel (`WEIGHT_NUMFMT`) и на печати, не округлены до целых кг: округлённые по отдельности строки не сходились с «Итого» на 1–2 кг. Ширина колонки веса в Excel (`computeColumnWidths`) — по тексту `fmt`, а не по длине числа (у `1000000` 7 знаков, на листе `1 000 000,000` — 13, иначе `#####`). ## Портал tallyman.nasekomuspro.ru

С 2026-10 сайтов два. Старый (GitHub Pages и `em.nasekomuspro.ru`) — открытые статические страницы, ведёт себя как раньше. Новый — **портал** `https://tallyman.nasekomuspro.ru`, название продукта **Tallyman** (решение пользователя 2026-10-18, тогда же домен переименован с `tools.nasekomuspro.ru` — DNS-записи `tools.` больше нет; тальман — тот, кто в порту сверяет груз с документами): бренд в верхней полосе (`shell-addon.js`), на страницах входа/приглашения, в `<title>` страниц портала и в темах писем (`mail.js`). Старый сайт по-прежнему «Лоция» — его не переименовывали. Те же инструменты, но за входом по почте и паролю, с правами на каждый инструмент, журналом работы и инструкциями. Файлы манифестов по-прежнему обрабатываются только в браузере и на сервер не уходят: сервер получает лишь ключ инструмента, **имена** файлов и текст итога (журнал). Код портала — `portal/`, новых зависимостей у старого сайта нет; спецификация — `docs/superpowers/specs/2026-10-18-tools-portal-design.md`.

- `portal/server/` — сервис на Node ≥ 22.13 (`node:sqlite` без флага; на сервере `nodejs` 22.22 из apt), без сборки. Единственная npm-зависимость сервиса — `nodemailer` (`dependencies`; `exceljs`/`jszip` остаются в `devDependencies`, нужны тестам и примерам); подключается **не при старте**, а динамическим `await import('nodemailer')` внутри `createMailer` (async), только когда задан `SMTP_HOST` — без почты сервис стартует и без пакета (Ruling R12). Пакет на чистом JS без зависимостей, поэтому на сервер (где нет `npm`) его копирует `deploy-tools.sh` из локального `node_modules/nodemailer/`. `main.js` — точка входа (переменные: `PORT`, `DB_PATH`, `SITE_ROOT`, `PUBLIC_ORIGIN`, `COOKIE_SECURE`, `SMTP_*`), `app.js` — маршруты и отдача файлов, `catalog.js` — каталог и права, `db.js` — база, `cli.js` — командная строка. `portal/web/` — страницы портала (вход, приглашение, главная, журнал, профиль, люди, запросы) и добавка к общему каркасу; `portal/help/` — инструкции к инструментам и `samples/` (синтетические примеры файлов, собирает `make-samples.js`).
- **Как сервер склеивает старый каркас с порталом**: страницы инструментов — те же файлы репозитория (`<key>/index.html`, `app.js`, `core.js`, `lib/*`), сервер отдаёт их только тем, у кого есть право на ключ (ключ — первый сегмент `href` в `tools.js`: `'bl-split/index.html'` → `bl-split`; у администраторов все ключи). Но три адреса сервер собирает сам: `/assets/style.css` = `assets/style.css` + `portal/web/theme.css` (палитра «Глубина», печать остаётся светлой), `/assets/shell.js` = `assets/shell.js` + `portal/web/shell-addon.js` (журнал, меню пользователя, справка), `/tools.js` — **генерируется на каждого пользователя** из корневого `tools.js` (только доступные ему инструменты). Поэтому **правка `assets/shell.js` или `assets/style.css` — проверить и портал** (склейка не должна сломаться, тёмная тема и печать — тоже); `?v=` в страницах портал не использует (заголовок `no-store` на каждый ответ).
- **Зависимости между инструментами** (Ruling R5): при старте сервер сам читает каждый `<key>/index.html` и ищет ссылки `<script src="../<другой-ключ>/…">`/`<link href=…>`; владельцу ключа A отдаются **не-HTML** файлы каталога B, от которого A зависит (так `grand-total-import` берёт `../grand-total/app.js`). HTML-страницы B по-прежнему требуют права на B. Заводить второй список зависимостей руками не нужно — он выводится из страниц.
- **Каталог и зависимости читаются один раз при старте.** Изменили `tools.js` или `index.html` инструмента — после `./deploy-tools.sh` сервис перезапускается (скрипт делает `systemctl restart`); без перезапуска новый инструмент не появится.
- Вход: почта нормализуется `trim().toLowerCase()`, сессия бессрочная (cookie `lt_session`, перевыпускается при каждом запросе, 400 дней; сессии лежат в базе — ночная перезагрузка сервера в 01:00 людей не разлогинивает), приглашение 7 дней, сброс пароля 24 часа, пароль ≥ 8 символов, неудачные входы за 15 минут блокируются раздельно: **10 по одной почте** и **30 с одного IP** (за одним адресом сидит несколько человек — опечатки одного не должны запирать остальных; 31-я попытка с IP — 429; IP берётся из `X-Real-IP`, его nginx **перезаписывает**, не дописывает; Ruling R11). «Забыли пароль?» — активному письмо сброса, приглашённому (в том числе с истёкшей ссылкой) письмо-приглашение, без почты — запрос администратору (`tool: null`) обоим; отключённому и неизвестной почте — ничего, ответ одинаковый. Изменяющие запросы без `Origin = PUBLIC_ORIGIN` — 403. При `PUBLIC_ORIGIN` на `https://` каждый ответ несёт `Strict-Transport-Security: max-age=31536000` (на `http://` — разработка — нет). Адреса `/portal/*` публичны, но отдают только не-HTML файлы (стили, скрипты, картинки, шрифты): любой `.html`/`.htm` оттуда — 404, страницы открываются только по своим адресам и за входом (Ruling R13). Хеш-приманка для неизвестной почты считается один раз при создании приложения.
- **«Показывать недоступные инструменты»** — настройка на каждого человека (`users.show_locked`), **по умолчанию выключена** (решение пользователя 2026-10-18): тогда человек о закрытых инструментах не узнаёт — `/api/me` отдаёт в `tools` только доступные, на главной у вкладок просто «N» (а не «N из M»), пустая вкладка — «Здесь вам пока ничего не выдано», страница закрытого инструмента и его справка — **404** «не найдено» (не 403 с кнопкой), `POST /api/requests` — 403 «Запросы доступа отключены». Включена — как раньше (карточки «Нет доступа», «Запросить доступ», 403-страница). Администратору не нужна. Галочка — в форме приглашения и в строке каждого коллеги на «Пользователях» (`PUT /api/admin/users/<id>/settings {showLocked}`, сохраняется сразу). Зависимости (R5) работают при любом значении. В тестах `addUser` по умолчанию создаёт человека с выключенной настройкой, как в рабочей базе; тесты кнопки «Запросить доступ» и 403-страницы передают `showLocked: true`.
- **Тестовая ссылка** (кнопка «Тестовая ссылка» на «Пользователях», `POST /api/admin/guests {name, tools, showLocked, hours}`): тестовый человек (`users.guest = 1`, без пароля, служебная почта `guest-<случайное>@guest.invalid` — в интерфейсе не показывается, вход по ней и «Забыли пароль?» не работают) и многоразовая ссылка `/guest/<токен>` (вид токена `guest`, в базе — хеш): открыл — сразу внутри (сессия, `302` на `/`), на любом числе устройств. Срок — 1–720 часов, по умолчанию 24, **от момента выдачи** (`users.expires_at`). Срок проверяется на каждом запросе (`app.js`): вышел — отключение, сессии и ссылки гаснут, запрос идёт как без входа; недействующая ссылка — `410` (`portal/web/guest-gone.html`). При старте и раз в сутки `dailyCleanup` (`portal/server/cleanup.js`, вместе с чисткой журнала) отключает просроченных, `GET /api/admin/users` — тоже перед ответом. В списке — «тест до ДД.ММ ЧЧ:ММ» / «тест истёк», действия «Инструменты», «Продлить» (`POST /api/admin/users/<id>/extend {hours}`: новый срок от текущего момента, статус «активен»; живые ссылки продлеваются, а если их нет — истекли или доступ отключали — в ответе новая ссылка), «Новая ссылка» (новый guest-токен на текущий срок, старые гаснут), «Отключить»; «Включить» у тестового нет (сервер — 409). Пароля у тестового нет: «Мой профиль» — только название и «Доступ до …», `POST /api/password` — 403.
- **Миграция базы**: `openDb` доводит базу прежней версии до текущей схемы сам (`migrate` в `db.js`) — недостающие колонки `users` добавляются `ALTER TABLE … ADD COLUMN`, а таблица `tokens` (у неё `CHECK` на вид токена, `ALTER` его не меняет) пересоздаётся одной транзакцией с теми же строками. Новые колонки — добавлять туда же, проверять тестом на файле со старой схемой (`db.test.js`).
- **Журнал** (`/journal`) хранит ключ инструмента, **имена** файлов и краткий итог из плиток результата — содержимого файлов нет; хранится 365 дней (чистится при старте и раз в сутки). Записи создаёт `portal/web/shell-addon.js`: «результат» — при `Shell.setResultShown(true)` после `false` (повторный `true` подряд запись не двоит), «скачивание» — при скачивании результата. Сервер принимает не больше 60 записей на человека за 10 минут (счётчик в памяти, дальше 429 и запись не создаётся).
- **От чего зависит журнал в старом сайте** (`shell-addon.js` читает страницу, не меняя её, — переименование любого из этих мест в старом сайте **молча ломает журнал**, тесты этого не поймают): `.file-list__name` (имена файлов; внутри `.file-list--results` не считаются), `.result__head .stat` с `.stat__value`/`.stat__label` (итог), `.result__actions .btn` (подпись скачивания), `.page__subtitle` (место для ссылки на справку), ссылка `a[download]`, которую страницы кладут в `document.body` перед щелчком (по ней фиксируется само скачивание), и `Shell.setResultShown` (подменяется обёрткой). Ruling R8: «результат» не двоится — запись не пишется, если файлы и итог те же, что уже записаны, хотя страница перед каждым запуском прячет прошлый результат (`createJournal` в `shell-addon.js`, тест в `shell-addon.test.js`).
- **Почта необязательна**: письма уходят, только если в `/etc/manifest-portal.env` задан `SMTP_HOST` (+ `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`). Без него портал работает полностью — ссылку-приглашение или сброс администратор копирует со страницы «Люди» и передаёт сам. Хостер на 2026-10-18 блокирует исходящие 25/465/587, поэтому пока SMTP не настроен.
- **Первый администратор** (и новая ссылка для существующего) — на сервере: `cd /opt/manifest-portal && set -a && . /etc/manifest-portal.env && set +a && runuser -u manifest-portal -- env DB_PATH="$DB_PATH" PUBLIC_ORIGIN="$PUBLIC_ORIGIN" node portal/server/cli.js add-admin <почта> <имя>`; в stdout — только ссылка-приглашение. Остальных людей администратор приглашает со страницы «Люди».
- **Сервер**: тот же VPS `130.49.213.189`, что и `em.nasekomuspro.ru`. Код — `/opt/manifest-portal` (владелец `manifest-portal`), сервис `manifest-portal` (юнит из `portal/deploy/manifest-portal.service`, слушает `127.0.0.1:$PORT`, `Restart=always`, `ProtectSystem=strict`, `UMask=0077`, `StateDirectory=manifest-portal` + `StateDirectoryMode=0700` — `/var/lib/manifest-portal` создаёт и отдаёт пользователю сам systemd, туда же единственное место записи; то же `StateDirectory` и `UMask` у `manifest-portal-backup.service`, поэтому копии пишутся тем же пользователем в `/var/lib/manifest-portal/backup`), настройки — `/etc/manifest-portal.env` (права 600), nginx — `portal/deploy/nginx-tallyman.nasekomuspro.ru.conf` (в файле плейсхолдер `__PORT__`, при установке заменяется на порт из env; **не** `default_server` — на сервере живут em, disp, NetBird; TLS — `certbot --nginx -d tallyman.nasekomuspro.ru`). ## Подводные камни

- Формат манифеста зашит в `lib/manifest-format.js` как константы (лист `"Manifest"`, шапка рейса — строки 3–5, заголовки колонок — строка 5, данные с 6-й, диапазон колонок заголовков C:Y, строка данных — A:Y от `ROW_FIRST_COLUMN`) — если реальный шаблон манифеста изменится, править только там, все `core.js` переиспользуют эти константы, а не дублируют числа.
- В `dg-check/core.js` колонки и сводного файла, и DG-манифеста ищутся по тексту заголовка, а не по фиксированной букве столбца — раскладка DG-манифеста официально не фиксирована. DG-манифесты — официальные международные документы, заголовки на английском («CNTR No.», «UN No.», «CLS(Sub)»), поэтому у контейнера и класса по два варианта ключевых слов (рус/англ) в `DG_SPECS`; при новых формулировках заголовков — добавлять туда, а не менять номер колонки.
- В `lib/port-breakdown.js` поиск колонок веса — по ключевым словам «груза»/«тары»/«общий», а не «вес» целиком: в реальных файлах-примерах заголовки написаны как «Веc груза»/«Веc тары»/«Общий Веc» с латинской `c` вместо кириллической (проверено побайтово), слово «вес» в них не встречается ни разу. Колонка-порт (назначения/отправления) ищется тем же приёмом — ключевые слова «назначения»/«отправления» не пересекаются, поэтому один и тот же поиск безопасен в обе стороны.
- `normalizePort` в `lib/port-breakdown.js` схлопывает не любые повторные пробелы, а именно пробел перед «(»: один и тот же порт в реальных данных встречается то как «…Port (RUPLP)», то как «…Port(RUPLP)» — отличие в наличии ровно одного пробела, а не в его количестве, поэтому `\s+\(` убирается до общего схлопывания `\s+`.
- В `lib/port-breakdown.js` строка без номера контейнера **не считается данными вообще** — это не только защита от пустых строк-разделителей, а прямое следствие реального файла: под последней строкой данных там стоит ещё одна строка с формулами `СУММ()` по весу (без контейнера, порта и типа), и раньше она проходила фильтр «есть хоть один вес» и удваивала итоговый вес всего файла. Номер контейнера — обязательная шестая колонка (ключевое слово «контейнера»), а не просто поле для показа. `buildManifestTotals` из-за этого же правила явно отказывает ошибкой «Не найдено ни одной строки с контейнером», если после фильтра не осталось ни одной строки данных — без этой проверки отчёт молча показал бы нулевой итог, как будто в манифесте нет груза (найдено при ревью, до выпуска, тестом).
- «Кол-во» в `lib/port-breakdown.js` — число **уникальных** номеров контейнера в группе, не число строк: один физический контейнер с несколькими видами груза в реальных манифестах занимает несколько строк с одним и тем же номером (проверено на реальном файле пользователя — три строки на контейнер `MSKU8627414`, разный вес на каждой строке). Вес при этом суммируется по каждой строке — это разные части груза одного контейнера, а не задвоенные записи. Подробности и как это обнаружилось — `.autopilot/2026-09-06-port-dashboard/spec.md`, раздел D01. Логика была сначала в `dashboard/core.js`, потом вынесена в `lib/port-breakdown.js` при добавлении `dashboard-departure/` — второй копии этого (уже однажды забагованного) кода заводить не стали.

Причина: реальная колонка «Опасные грузы» пишется не этим сайтом и использует свои разделители (`;\r` вместо `" / "`) и группировку («IMO 9 UN 3077,3082» вместо двух отдельных записей) — точное сравнение текста давало расхождение почти на каждой строке при одинаковых по сути данных (проверено на реальных файлах пользователя: было 71 «расхождение» вместо 2 настоящих).

Поэтому все ссылки на свой JS (`<script src="...">`/`<script type="module" src="...">` — `tools.js`, `assets/shell.js`, `app.js` — во всех четырнадцати страницах: `index.html`/`merge/index.html`/`dg-check/index.html`/`dashboard/index.html`/`dashboard-departure/index.html`/`bl-split/index.html`/`grand-total/index.html`/`grand-total-import/index.html`/`order-check/index.html`/`bl-registry/index.html`/`template-check/index.html`/`source-check/index.html`/`source-audit/index.html`/`arm-upload/index.html`, и `import ... from '...core.js?v=...'`/`'...manifest-format.js?v=...'`/`'...port-breakdown.js?v=...'` внутри `app.js`/`core.js`) и все ссылки на `assets/fonts.css` и `assets/style.css` (`<link rel="stylesheet" href="...">` в каждом из тех же `index.html`) несут `?v=<YYYYMMDDHHMM>`. **При каждой правке `core.js`/`app.js`/`manifest-format.js`/`port-breakdown.js`/`tools.js`/`assets/shell.js`/`assets/fonts.css`/`assets/style.css` — обновляй это число везде, где встречается**, иначе фикс не долетит до уже открытых вкладок ещё 10 минут (это уже случалось дважды: с JS — жена тестировала правки со старым закэшированным кодом и ловила старые баги; с `style.css` — после добавления вкладок «Экспорт»/«Импорт» браузер подставил старые стили без правила `.tool-grid[hidden]`, и обе вкладки показывались одновременно, хотя новая разметка уже пришла; теперь на это есть глобальное `[hidden]{display:none!important}`). `tools.js`, `assets/shell.js`, `fonts.css` и `style.css` не участвуют в цепочке импортов `core.js`/`app.js` (обычные `<script>`/`<link>` на каждой странице), поэтому их `?v=` меняется независимо, но так же на всех четырнадцати страницах. Правка `lib/manifest-format.js` или `lib/port-breakdown.js` тянет за собой каскад: у них меняется число → у всех `core.js` **и `app.js`**, что их импортируют (`countDataRows` из `manifest-format.js` импортируют напрямую `app.js` всех страниц, кроме `bl-split` и `template-check` — он этот модуль не использует вовсе), меняется содержимое строки импорта → у `app.js` меняется строка импорта `core.js` → у их `index.html` меняется `<script src="app.js?v=...">`. Обновлять нужно всю цепочку, а не только сам изменённый файл. Сами `index.html` страниц `?v=` не несут (их адрес не версионируется), поэтому браузер — в том числе с локального дев-сервера — может показать закэшированную **старую разметку** страницы при новых скриптах/стилях или наоборот: после правки `index.html` проверять с жёсткой перезагрузкой (Cmd+Shift+R), а не делать выводы о баге по обычной.
- `grand-total/app.js` рисует PDF не встроенными 14 шрифтами `pdf-lib` (`PDFLib.StandardFonts.Helvetica`) — их WinAnsi-кодировка не содержит кириллицу вовсе, `page.drawText('ВЫГРУЗКА ...')` бросает исключение прямо внутри `pdf-lib` (найдено при ручной проверке в браузере на реальном файле). Вместо этого шрифт (Roboto) грузится с постоянного версионированного URL `fonts.gstatic.com/s/roboto/v51/...ttf` и встраивается через `@pdf-lib/fontkit` (единственная зависимость сайта не с cdnjs — берётся с `cdn.jsdelivr.net`, на cdnjs `fontkit`а нет) с `embedFont(bytes, { subset: true })`. **Не через Google Fonts CSS API с `text=<нужные символы>`** (первая попытка): тот вариант отдаёт уже урезанный на сервере `.woff2`, и с этой же версией `pdf-lib` (`1.17.1`) и `@pdf-lib/fontkit` (`1.1.1`) он либо зависает на `doc.save()` без ошибки и без таймаута, либо — если отключить повторное подрезание (`subset: false`) в обход зависания — даёт неверную раскладку глифов (текст читается как случайный набор символов). Обычный статический `.ttf` с постоянного URL обеих проблем не имеет. Roboto — единственный внешний шрифт на сайте и нужен только внутри PDF; шрифты интерфейса (Onest/JetBrains Mono) встроены в `assets/fonts.css` и к PDF отношения не имеют — редизайн интерфейса этот шрифт не заменяет.
- В Excel-выгрузке `grand-total/app.js` веса — числа с `numFmt` (`#,##0.000" KGS"`), а не готовый текст «8 692 506,220 KGS»: `numFmt`, поставленный на строковую ячейку, в Excel не действует (ячейка остаётся текстом, не числом). Поэтому у Excel-строк — свой источник (`buildExcelRows`), с сырыми `entry.cargoWeight`/`entry.tareWeight`/`entry.totalWeight`, а не общий с PDF и предпросмотром `buildTableRows` (там вес уже отформатирован в текст — то, что нужно для `page.drawText`, но не для числовой ячейки). Ширина колонок Excel-листа при этом всё равно считается по отображаемому тексту (число, прогнанное через тот же `formatWeight`, что и в PDF), а не по длине самого числа — иначе колонка веса окажется у'же, чем нужно для « KGS».
- Заголовки и подписи шапки поручения в `lib/loading-order.js` (`TABLE_HEADERS`/`findTableColumns` — колонки таблицы контейнеров; `HEADER_LABELS`/`FIELD_BY_LABEL` — подписи шапки) ищутся точным совпадением текста ячейки (после `trim().toLowerCase()`), не вхождением подстроки: «брутто груза» — подстрока заголовка «Брутто груза с весом контейнера», «Номер поручения» соседствует с «Номер поручения (Э)», «Отправитель» — с «Отправитель (англ)»; нестрогий поиск задел бы не ту колонку/подпись, и веса разошлись бы систематически на вес тары. Было в `order-check/core.js`, перенесено при выделении общего модуля — им пользуются и `order-check`, и `template-check`.
- Строки поручения с наименованием груза «поддоны»/«поддон»/«палеты»/«палета»/«паллеты»/«паллета»/«средства крепления»/«средство крепления» (`PALLET_CARGO_NAMES` в `lib/loading-order.js`, было в `order-check/core.js` до выделения общего модуля) исключаются из веса груза контейнера — вес тары упаковки или крепления, не содержимого (крепление — реальное поручение 7838133940-P26-00179 от 2026-10-18: 100 кг под каждым контейнером, в шаблоне в «ВЕС ГРУЗА» не входят, в ВГМ — входят; без исключения «Проверить шаблон» дал 30 ложных ошибок веса). Сравнение тоже точное (`trim().toLowerCase()` в `Set.has`), не по вхождению: под нестрогое совпадение «поддон» иначе попала бы реальная позиция груза «поддон анализатора ситового» и её вес пропал бы из сверки.
- Сопоставление контейнер↔поручение в `crossCheckOrders` — сперва по паре ключей `` `${номер поручения}::${номер контейнера}` `` (`index`), и только если пары нет — откат на поиск контейнера по одному ключу среди всех поручений (`containerToOrders`), с пометкой «поручение указано неверно». Оба индекса строятся заранее по всем загруженным поручениям, потому что один контейнер в реальных данных может стоять под несколькими поручениями (сборный/групповой контейнер) и первое совпадение — не обязательно то, что записано в своде.
- Соответствие «код ISO → футность» в `crossCheckOrders` не зашито константой, а строится на лету по большинству (`isoFrequency`/`isoToFutnost`): для каждого ISO-кода, встретившегося у сопоставленных контейнеров текущей загрузки, берётся футность, которая чаще всего стоит в своде рядом с этим ISO. Официального справочника ISO→футность на сайте нет ни в одном модуле, а завести его константой означало бы держать её в синхроне с кодами, которых в реальных поручениях могло и не быть.
- Общий вес в `crossCheckOrders` сравнивается не с суммой столбцов «Веc груза»/«Веc тары» самого свода, а с суммой этих же величин, взятых из поручения (тех же, что уже сверяются как вес груза/тары по отдельности) — иначе строка, где общий вес перепутан со значением соседней при сборке свода (реальный случай, найденный на файле пользователя), осталась бы незамеченной, если бы вес груза и тары сами по себе совпали.
- `stripWhitespace` в `bl-registry/core.js` убирает вообще все пробельные символы, а не схлопывает их в один — перенос строки внутри номера поручения в реальных данных должен пропадать без следа, а не превращаться в пробел (проверено побайтово на приложенном пользователем файле, см. `.autopilot/2026-09-12-orders-bl-registry--wip/reference.md`). Ячейка «№ поручения» с несколькими номерами через `"; "` — второй (и далее) может быть обрезанным хвостом, а не отдельным номером: `splitOrderNumbers` достраивает такой хвост недостающим префиксом первого номера пары по длине, только когда кусок короче базового — проверено вычислительно на обоих реальных случаях из приложенного файла, совпадает посимвольно.
- `buildOrdersRegistry` дедуплицирует пары не по одному полю, а по ключу «поручение+коносамент» (`` `${order} ${bl}` ``) — один коносамент под несколькими поручениями и один номер поручения на несколько коносаментов в реальных данных не редкость, каждая уникальная пара — своя строка реестра; строка, где оба поля пустые, пропускается, а с пустым только одним из двух — остаётся. Сортировка результата — обычное строковое сравнение по номеру коносамента, не `localeCompare`: порядок исходного эталонного документа восстановить всё равно нельзя (сам документ не сохранился), а `localeCompare` дал бы разный порядок кириллицы/латиницы в разных браузерах.
- Эталонная форма шаблона в `template-check/template-form.js` построена по шаблону первой реальной заявки (2026-09-28, «Шаблон эл. поручения серпентинит.xlsx»; прежняя форма на 26 колонок A:Z с шапкой в D/E — по двум образцам из `.autopilot/2026-09-12-order-template-check--wip/reference.md`, старые шаблоны теперь приводятся к новой форме как «исправлю сам»), а не по документации системы: официального описания формата загрузки на сайте нет (та же ситуация, что с манифестом и `lib/manifest-format.js`). Точность подписи шапки/заголовка колонки в `template-check/core.js` при этом сравнивается после `trim()` — пробелы по краям текста не считаются «неточным заголовком» (известный некритичный зазор, не путать с ошибкой определения формы).
- Сравнение ISO-кода в `template-check/core.js` (`sameIsoType`/`parseIso`) — не точным текстом, а по типу контейнера (длина + группа + высота, где она известна с обеих сторон): обиходное обозначение, официальный 4-значный ISO-код и старый 4-значный числовой код кодируют один и тот же тип по-разному — `ISO_COMMON`/`ISO_LENGTH`/`ISO_HEIGHT`/`ISO_OLD_GROUPS` разбирают их в `{length, height, group}` и сравнивают структуры, а не строки (тест: «2200 ≡ 22G1, 4532 ≡ 40RH, 40DV ≢ 45G1» — «40DV» и «45G1» отличаются высотой, STD и HC). Не разобрался хотя бы один код с обеих сторон — откат на сравнение строк без учёта регистра.
- Строка «итого» в `template-check/core.js` (`isTotalRow`) — строго «без номера контейнера, заполнены только колонки Q–U (`places`/`cargoWeight`/`tareWeight`/`volume`/`vgm`) числами»: любая непустая ячейка вне этих пяти колонок — в том числе с меткой «Итого»/«Всего»/«Total» — это уже не «только Q–U», такая строка идёт в отдельное правило «без контейнера, но с данными» (уточнить у заказчика), а не удаляется молча вместе с настоящим «итого».
- `checkBillGroups` в `template-check/core.js` — у строк одного коносамента дата и место издания коносамента, терминал выгрузки, PRE-CARRIAGE BY/PLACE OF RECEIPT/PLACE OF DELIVERY, условия поставки и тип перевозки, SHIPPER/CONSIGNEE/NOTIFY и их адреса должны совпадать (защита от протягивания данных в Excel: если строку скопировали и не поправили одну ячейку, это не должно пройти незамеченным). Расхождение — `level:'error', fix:'customer'`, никогда не `'auto'`: при разных значениях в двух строках нельзя знать, какая из них верна, а какая испорчена, поэтому решение всегда за заказчиком. Красится **каждая** расходящаяся строка (не только первая встреченная); первая строка коносамента — эталон сравнения и сама не помечается.
- В `template-check/core.js` (`buildMarkedWorkbook`) заливка ячейки зависит от уровня находки: ошибка — **оранжевый** (`ERROR_ARGB`, `FFFF9900`), предупреждение — голубой (`BLUE_ARGB`, `FFADD8E6`); если у одной ячейки и то и другое (по разным правилам), красится оранжевым — ошибка важнее. Не жёлтый, как в `dg-check`/`order-check`: в новой форме заказчик сам заливает жёлтым все обязательные графы, и жёлтая пометка ошибки на них не видна (решение пользователя 2026-09-28). Ярлык листа с ошибкой — тоже оранжевый.
- Номер контейнера и пломбы в `template-check/core.js` сопоставляются с поручением с заменой кириллицы-двойника на латиницу (`toLatin`), но сама запись с кириллицей — ошибка «исправлю сам» с пометкой «кириллические буквы вместо латинских» (реальный случай — пломба «Р0217711» с русской «Р»: на вид не отличить). В графах ТЕМПЕРАТУРА/ОПИСАНИЕ КЛАССОВ ОПАСНОСТИ «-», «NOT IMO», «NON DG», «нет» (`NONE_MARK`) — это «ничего нет», а не текст: у рефконтейнера такая температура — предупреждение, при опасном грузе в поручении такой класс — ошибка.
- «КОЛИЧЕСТВО МЕСТ» (`places`) в `template-check/core.js` сверяется с поручением, но никогда не исправляется в загруженном шаблоне автоматически — только `fix:'customer'` (или предупреждение, если товаров в поручении несколько и расхождение могло возникнуть из-за упаковки в одно место); ключ `places` стоит в `KEEP_AS_IS_KEYS` вместе с `billOfLading`/`billDate`/`cargoNameEn`/`packageType`/`volume`/`arrivalDate`/`departureDate` — списком-страховкой, который не даст завести авто-исправление для этих колонок, даже если его попробует завести новое правило.
- ВГМ (`vgm`) в `template-check/core.js` сверяется неравенством, не точным совпадением: ошибка только если ВГМ меньше веса груза с тарой по поручению (`num.number < sum - TOLERANCE`) — ВГМ физически не может быть меньше веса груза с весом контейнера, но может быть больше (упаковка, крепёж), и это не расхождение. Авто-исправление предлагается, только если «Брутто груза с весом контейнера» из поручения само не меньше этой суммы — иначе (например, у поручения тоже нет надёжного числа) находка уходит на `fix:'customer'`.
- ТЕРМИНАЛ ВЫГРУЗКИ в шапке (F7) в `template-check/core.js` сверяется с «Порт выгрузки» поручения (`orderInfo.dischargePorts`, тот же приём, что у СУДНО/РЕЙС — единственное известное значение по всем загруженным поручениям, иначе «уточнить у заказчика») — но не точным текстом: реальные образцы пользователя называют один и тот же порт по-разному («El Dekheila(EGEDK)» в поручении, «El Dekheila Alexandria Int. Container Terminal» в шапке), поэтому `samePort` в `template-check/core.js` отбрасывает скобочный код в конце (`stripPortCode`) и сравнивает вхождением в любую сторону, не строкой целиком.
- Заливка «шаблона с пометками» и «исправленного шаблона» — общая функция `paintFindings` в `template-check/core.js`: ошибка оранжевым, предупреждение голубым (поверх жёлтой заливки обязательных граф формы). В исправленном шаблоне красятся только находки с `fix !== 'auto'` (то, что осталось незакрытым) — по карте адресов `addressMap`, которую `buildCorrectedWorkbook` строит по ходу переноса значений (адрес на исходном листе → адрес той же ячейки в исправленном), а не по буквальному совпадению адресов: пустые/итоговые строки убраны, лишние колонки убраны, недостающие добавлены — при сдвиге строки или колонки находка обязана попасть на новый адрес, а не остаться там, где её уже нет.
- **ExcelJS 4.4.0 умеет прочитать условное форматирование любого типа, но при записи поддерживает только `expression`/`cellIs`/`top10`/`aboveAverage`/`dataBar`/`colorScale`/`iconSet`/`containsText`/`timePeriod`** (см. `node_modules/exceljs/lib/xlsx/xform/sheet/cf/cf-rule-xform.js` — `render()` там `switch` без `default`, для остальных типов просто ничего не пишет). Правило типа `duplicateValues` (подсветка повторов — реально встретилось в файле пользователя, колонка «Футность») в этом случае пишется как пустой `<conditionalFormatting/>` без `<cfRule>` внутри — невалидно по схеме OOXML, Excel при открытии предлагает восстановить/удалить нечитаемое содержимое. Баг библиотеки, воспроизводится даже на чистой загрузке-сохранении без единой собственной правки (`workbook.xlsx.readFile()` → `writeFile()`), пересоздание правила через `addConditionalFormatting()` не помогает — проблема в самом рендере `cfRule`, не в модели. Обход — `dropUnwritableConditionalFormatting` (сейчас общий модуль `lib/xlsx-safe-write.js`, до выделения жил прямо в `order-check/core.js`): убирает из `sheet.conditionalFormattings` любые правила не из этого белого списка — сама подсветка дублей при этом теряется, но файл остаётся читаемым, что важнее. Вызывают его `crossCheckOrders` (`order-check/core.js`, раз на сводный лист) и `checkTemplate` (`template-check/core.js`, в `buildMarkedWorkbook` — по разу на каждый лист книги с пометками). Сборка ведётся навыком `/autopilot`. Требования, спецификация и таски — в `.autopilot/`.
Прогресс — `.autopilot/dashboard.html`. Правило: требование из `manifest.md`
может снять только пользователь.

Если работа продолжается — скажи «продолжи автопилот»: состояние поднимется
из `.autopilot/state.js`, переспрашивать ничего не нужно.
