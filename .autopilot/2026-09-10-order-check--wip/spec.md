# Спецификация: Сверка сводного манифеста с поручениями на погрузку

## Задача

Сводный файл манифеста собирается вручную из десятков и сотен отдельных
поручений на погрузку, которые присылают клиенты — по контейнеру, весу,
пломбе, типу контейнера, номеру поручения, классу опасного груза. На таком
объёме (в примере пользователя — 111 поручений, 673 строки свода) ошибка
при переносе данных неизбежна и легко проходит незамеченной: контейнер
попадает не под тем поручением, вес перепутан между соседними строками,
номер пломбы читается неверно. Сейчас это можно проверить только вручную,
построчно сверяя каждый контейнер с исходным поручением — то, что уже
один раз было сделано разовым скриптом и нашло реальные ошибки (5 строк
с перепутанными весом/пломбами, опечатки в пломбах, пропущенный номер ООН
опасного груза).

## Решение

Новый инструмент сайта: загружаете сводный файл манифеста и все поручения
на погрузку (архивом .zip, как приходит с почты, или отдельными файлами) —
инструмент сверяет каждый контейнер сводного файла с его поручением по
весу груза, весу тары, номеру пломбы, типу контейнера, номеру поручения
и классу опасного груза, дописывает в сводный файл столбец «Несовпадения»
с описанием каждого расхождения и закрашивает строки с расхождениями
жёлтым. Результат скачивается как обычный .xlsx — можно открыть, проверить
подсвеченные строки и поправить исходный свод.

## Решения по реализации

1. Новый каталог `order-check/` — `index.html`, `app.js`, `core.js`, `core.test.js`, по образцу `dg-check/`. Добавляется карточка в `tools.js` (R11).
2. `core.js` не импортирует ExcelJS/JSZip сам — получает готовые `ExcelJS.Workbook` снаружи, как все Excel-инструменты сайта; тестируется в Node через `import('exceljs')`.
3. Единственный экспорт: `crossCheckOrders(combinedWb, orderEntries) -> {ok:true, resultWorkbook, summary} | {ok:false, error}`, где `orderEntries: Array<{fileName, workbook}>` — тот же принцип входных примитивов, что в `dg-check`, только поручений много, а не одно.
4. Колонки сводного файла ищутся по ключевым словам в `COLUMN_HEADER_ROW` (как в `dg-check`/`port-breakdown.js`, те же константы из `lib/manifest-format.js`): контейнер → «контейнера», футность → «футность», вес груза → «груза», вес тары → «тары», пломбы → «пломбы», опасные грузы → «опасн», номер поручения → «поручения». Все ключевые слова проверены на реальном списке заголовков свода — коллизий с другими колонками нет (например, «Негабаритные грузы(см)» не содержит «груза» — только «грузы»).
5. Колонки поручения ищутся **точным** совпадением текста заголовка (после trim), а не вхождением подстроки: «Брутто груза» — подстрока заголовка «Брутто груза с весом контейнера», и нестрогий поиск задел бы не ту колонку. Строка заголовков находится по первой колонке со значением «Номер контейнера» среди первых ~15 строк листа (тем же приёмом, что поиск шапки в `dg-check`), а не по фиксированному номеру строки.
6. Группировка строк одного контейнера внутри поручения: строка с непустой первой колонкой («Номер контейнера») начинает новую группу и несёт код ISO, номер пломбы, вес тары, класс/код опасности; последующие строки с пустой первой колонкой — дополнительные позиции груза того же контейнера (несут только вес и наименование). Строка, где первая колонка точно равна «Дополнительные сведения», — конец таблицы (обнаруженный маркер конца, одинаковый во всех поручениях-примерах).
7. Вес груза контейнера = сумма «Брутто груза» по всем строкам группы, **кроме** строк, где «Наименование груза» после trim и приведения к нижнему регистру точно равно одному из: «поддоны», «поддон», «палеты», «палета», «паллеты», «паллета» (реализует R01/R03 — в брифе названы оба слова, «поддоны» и «палеты»; в разборе реальных данных пользователя встретилось только «поддоны», но вариант с «палет-» включён на случай других поручений). Сравнение точное, не по вхождению подстроки — иначе под исключение случайно попала бы настоящая позиция груза вроде «изделие из черных металлов: поддон анализатора ситового» (реальный случай из данных пользователя). Вес тары = «Вес контейнера» со строки самого контейнера. Сравнение с допуском 0.01 кг.
8. Класс опасности контейнера = множество пар «класс\|UN» по всем строкам группы, где заполнены и «Класс опасности», и «Код опасности» (ячейка кода опасности может содержать несколько UN через запятую — каждый разбирается в отдельную пару). Сравнение со сводным файлом — тем же приёмом, что в `dg-check`: текст «Опасные грузы» разбирается тем же регулярным выражением `IMO … UN …` в множество пар и сравнивается без учёта порядка и группировки.
9. Сопоставление контейнера с конкретным поручением — по паре (номер поручения, номер контейнера), а не по одному номеру контейнера: один контейнер в реальных данных может быть распределён на два поручения (сборный груз, у пользователя встречалось 8 раз из 665 контейнеров). Номер поручения из свода нормализуется (убираются переносы строк и повторные пробелы) перед сопоставлением. Если по нормализованной паре ничего не нашлось — ищем контейнер по номеру среди всех загруженных поручений: нашли в одном — сверяем по нему и добавляем пометку «поручение указано неверно»; не нашли нигде — отдельная пометка, остальные поля строки не сравниваются.
10. Соответствие «код ISO → футность» строится на лету по данным самой загрузки — по большинству среди совпавших по ключу (поручение, контейнер) строк, а не зашивается заранее (тот же принцип, что уже применяется на сайте: искать по содержимому загруженных файлов, а не по фиксированному списку). Для кода, встретившегося один раз, сравнивать не с чем — такая строка не помечается.
11. Пломбы сравниваются как множества строк (разбор по запятой/точке с запятой, `trim().toUpperCase()`, без учёта порядка).
12. Расхождения по строке склеиваются в одну ячейку через «; » в новом столбце `LAST_COLUMN + 1` с заголовком «Несовпадения»; при любом расхождении — весь диапазон `C:<новый столбец>` заливается жёлтым (`FFFFFF00`). Перед записью стиля он клонируется (`cloneStyle`), не мутируется напрямую — тот же приём и по той же причине, что в `dg-check`/`merge` (ExcelJS отдаёт один объект стиля многим ячейкам сразу).
13. Приём поручений: `<input type=file multiple accept=".xlsx,.zip">` + drag-and-drop, как в `merge`/`dashboard`. Файл `.zip` разворачивается в браузере через JSZip (та же версия `3.10.1` с cdnjs, что уже используется в `bl-split`) — из архива берутся только записи `*.xlsx`; служебные записи (`__MACOSX/…`, `.DS_Store`, каталоги) молча пропускаются. Отдельно выбранные `.xlsx`-файлы участвуют наравне с файлами из архива — можно и то, и другое в одной загрузке.
14. Файл, который не читается как `.xlsx` (повреждён или не тот формат) — не останавливает всю проверку: попадает в список предупреждений на странице с указанием имени файла (по образцу `warnings` в `bl-split`), остальные файлы обрабатываются как обычно.
15. Сводка на странице (по образцу `dg-check`): число строк с расхождениями по категориям (вес груза/тары, пломбы, тип, поручение, опасные грузы), число контейнеров из поручений, не найденных в своде, и список предупреждений о нечитаемых файлах.
16. Версионирование `?v=<YYYYMMDDHHMM>` — на все собственные ссылки (`index.html`, `app.js`, `core.js`, импорт `../lib/manifest-format.js?v=...`) при каждой правке этих файлов, как того требует уже действующее правило сайта (кэш GitHub Pages на 10 минут).
17. `order-check/index.html` использует `<script type="module">` для `app.js` — как `merge`/`dg-check`, страница требует http(s) (локальный сервер или GitHub Pages), не `file://`.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `order-check/core.js` | логикой сверки: группировка строк поручения, сопоставление контейнер↔поручение, правила веса/пломб/типа/опасных грузов, построение столбца и заливки | `crossCheckOrders(combinedWb, orderEntries) -> {ok, resultWorkbook, summary} \| {ok:false, error}` | поиск колонок (свода и поручений), группировку многострочных контейнеров, карту ISO→футность, разбор опасных грузов, сравнение пломб как множеств |
| `order-check/app.js` | состояние страницы: выбор/разбор файлов (включая распаковку zip через JSZip), вызов `core.js`, рендер сводки и предупреждений, скачивание результата | — (обычный DOM-скрипт, без публичного API) | — |

Тест-шов — один, `crossCheckOrders`: поведение проверяется через него, как и у остальных Excel-инструментов сайта. `app.js` тестами не покрывается — чистый DOM, как и другие `app.js` на сайте.

## Вне рамок

| Требование | Почему не сейчас |
|---|---|
| R07 — сверка отправителя/получателя | в своде эти поля на английском (перевод), в поручении — оригинал на русском; дословно почти никогда не совпадают даже при полностью верных данных (проверено на реальных данных пользователя: 327 «разных» отправителей и 354 «разных» получателя из 673 строк — без единой настоящей ошибки). Автосверка такого поля была бы только шумом |
| R07 — сверка количества мест | во многих поручениях это поле не заполняется отправителем (стоит 0) — не ошибка свода, а пробел в поручении. Проверено на реальных данных: 158 из 673 строк дали бы расхождение без единой настоящей ошибки |
