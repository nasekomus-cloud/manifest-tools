# Спецификация: Итоговый PDF-отчёт по манифесту («Grand Total»)

## Задача

Судовой агент выгружает манифест (иногда — несколько файлов на один рейс) и должен
за один шаг получить единый сводный отчёт: сколько всего контейнеров каждого типа,
какой у них суммарный вес груза/тары/всего — в виде готового к печати и отправке PDF,
а не таблицы, которую ещё придётся оформлять руками. Часть шапки этого отчёта —
позывной судна, дата прибытия, терминал выгрузки — в самом манифесте не встречается
ни в каком виде, и это не баг парсинга: этих данных там просто нет. Единственный
способ их туда доставить — вписать самому.

## Решение

Новый инструмент на сайте: загружаешь один или несколько файлов манифеста (тот же
формат, что и в остальных инструментах сайта), вписываешь в три поля позывной,
дату прибытия и терминал выгрузки — и скачиваешь готовый PDF с шапкой рейса и
таблицей «GRAND TOTAL»: по каждому типу контейнера — количество, вес груза, вес
тары, общий вес, и итоговая строка по всем типам сразу. Вид — по образцу,
приложенному пользователем вместе с задачей (`reference.md`).

## Решения по реализации

**Новый инструмент — `grand-total/`** (`index.html`, `app.js`, `core.js` + `core.test.js`), той же формы, что и остальные Excel-инструменты сайта: `core.js` не импортирует ExcelJS и PDF-библиотеку сам, а получает готовые `ExcelJS.Workbook` снаружи — тестируется в Node без браузера. Сборка самого PDF (единственное место, которому нужен `pdf-lib`) — в `app.js`, по аналогии с тем, как сборка Excel-отчёта сейчас живёт в `dashboard/app.js`, а не в `dashboard/core.js`.

**`lib/manifest-format.js` — новая функция `readVoyageHeader(workbook)`.** Строка 3 листа «Manifest» в примере пользователя содержит `Список на погрузку т/х GUANG QI DE ER TA` в одной ячейке и `Рейс №2601W` в другой — но не в фиксированных колонках C и J (это не проверено ни на одном втором файле), а как обычный текст в строке. Функция ищет по всей строке `HEADER_FIRST_ROW` ячейку, текст которой содержит «т/х», и берёт всё после «т/х» как название судна; ищет ячейку с «Рейс» и берёт то, что после «№» (или после самого слова «Рейс», если «№» нет), как номер рейса. Не находит — возвращает `null` в соответствующем поле, не бросает ошибку (R08i.1). Один и тот же приём поиска по ключевому слову, что уже используется в `lib/port-breakdown.js` и `dg-check/core.js` — не выдумываем второй способ там, где уже есть работающий.

**`lib/port-breakdown.js` — новая функция `buildManifestTotals(workbooks)`.** Переиспользует уже существующие в файле приватные помощники (`cellText`, `cellNumber`, `findColumnByKeyword`, `normalizeType`, `normalizeContainer`, `emptyGroup`/`addToGroup`/`finalizeGroup`, `validateStructure`) — те же правила подсчёта, что и в `buildPortBreakdownDashboard`: строка без номера контейнера не считается данными вовсе (СУММ()-строка внизу листа), «Кол-во» — число уникальных контейнеров, а не строк, вес суммируется по каждой строке. Отличие от `buildPortBreakdownDashboard` — группировка только по типу контейнера (Футность), без колонки порта вовсе, и без разбивки на `perFile`: этому инструменту нужен один общий («big file») итог по всем загруженным файлам сразу, как один рейс, а не свод с разбивкой по каждому файлу (в отличие от дашбордов, здесь одна PDF-таблица, не «лист на файл»). Заодно, тем же проходом по строкам, ищет колонку «коносамента» (тот же приём, что `findColumnByKeyword` в `dg-check/core.js` и `merge/core.js`) и считает число уникальных нормализованных (`trim().toUpperCase()`) значений — `billsOfLading`; колонка не найдена → `null` (тот же смысл «не 0, а не нашли», что уже принят в `merge/core.js`).

```
buildManifestTotals(workbooks)
  -> { ok: true,
       byType: [{ type, count, cargoWeight, tareWeight, totalWeight }],  // порядок — по первому появлению в данных
       grandTotal: { count, cargoWeight, tareWeight, totalWeight },
       billsOfLading: number | null }
  | { ok: false, error: string }
```

**`grand-total/core.js` — `buildGrandTotalData(workbooks)`.** Трёхстрочная обёртка (по образцу `dashboard/core.js` над `buildPortBreakdownDashboard`): вызывает `buildManifestTotals`, добавляет `readVoyageHeader` первого файла (тот же файл, что становится «эталонным» для проверки структуры в `validateStructure` — раз он уже играет роль первого/базового, брать шапку рейса больше не с кого).

```
buildGrandTotalData(workbooks)
  -> { ok: true, vessel: string|null, voyage: string|null,
       byType: [...], grandTotal: {...}, billsOfLading: number|null }
  | { ok: false, error: string }
```

**`grand-total/app.js` — DOM + PDF.** Дропзона и список файлов — переиспользуют `.dropzone`/`.btn`/`.file-list`/`.error-message` из `assets/style.css`, как во всех остальных инструментах. Три текстовых поля (позывной, дата прибытия, терминал) — обычные `<input type="text">`, не `<input type="date">`: эталон показывает дату как «08.09.2026», а типизированный date-инпут отдаёт эту дату в своём собственном формате в зависимости от локали браузера — свободный текст гарантирует ровно тот вид, который впишет пользователь. Кнопка «Скачать PDF» отключена, пока файлы не загружены и отчёт не посчитан; при нажатии — если любое из трёх полей пустое (после `trim()`), показывается `.error-message` с указанием, какое поле не заполнено, скачивание не начинается (R05.1/R06.1/G01.1).

Сборка PDF — через уже используемый на сайте `pdf-lib` (та же версия `1.17.1`, что и в `bl-split/index.html` — новую версию не заводим ради одного инструмента, раз работающая уже есть на сайте): `PDFDocument.create()`, одна страница альбомной ориентации (A4 landscape — шапка рейса и таблица в эталоне широкие, четыре-пять полей в один ряд), текст и линии таблицы рисуются вручную поверх страницы — таблица здесь маленькая (число строк равно числу разных типов контейнеров в манифесте, на практике заведомо меньше десятка), готового решения для таблиц в `pdf-lib` нет и не нужно. Если строк типов больше, чем помещается на одну альбомную страницу (courtesy-запас на нетипично разнообразный манифест) — добавляется вторая страница `pdf-lib`'ом тем же кодом, а не падает с обрезанной таблицей.

**Шрифт — не `StandardFonts.Helvetica` (см. D01 в манифесте).** Строка «ВЫГРУЗКА» из эталона и терминал, который агент может вписать кириллицей, не рисуются встроенными 14 шрифтами PDF — их WinAnsi-кодировка не содержит кириллицу вовсе, `page.drawText` с такой строкой бросает исключение прямо внутри `pdf-lib`. Вместо этого — обычный статический `.ttf` шрифта Roboto с постоянного, версионированного URL Google Fonts (`fonts.gstatic.com/s/roboto/v51/...` — Google не переиздаёт и не удаляет такие URL задним числом, в отличие от динамических `/l/font?kit=...`), встроенный через `@pdf-lib/fontkit` (UMD-сборка с `cdn.jsdelivr.net`, единственная зависимость сайта не с cdnjs — `fontkit`а там нет) с `embedFont(bytes, { subset: true })`: `pdf-lib` сам обрезает шрифт до реально нарисованных на странице символов.

Числа форматируются вручную (группировка по три цифры обычным пробелом, запятая — разделитель дробной части, три знака после неё, суффикс « KGS») — не через `toLocaleString('ru-RU')`, у которого группирующий пробел — Unicode U+00A0, а вручную собранная строка гарантированно совпадает с тем, что показывает эталон, независимо от рантайма браузера.

Строка типа контейнера форматируется из сырого значения Футности («20DC», «40HC» → «20'DC», «40'HC»): цифры в начале, апостроф, буквенный код — тот же вид, что в эталоне («386x20'DC»).

Имя скачиваемого файла — `grand-total-<voyage>.pdf` (номер рейса в нижнем регистре, без «№», без пробелов), если рейс распознан; иначе `grand-total-report.pdf`.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `lib/manifest-format.js` | формат шапки манифеста (строки 3–5) | + `readVoyageHeader(workbook) -> {vessel, voyage}` (оба — `string \| null`) | поиск по ключевому слову внутри строки шапки |
| `lib/port-breakdown.js` | подсчёт весов и дедупликацию контейнеров | + `buildManifestTotals(workbooks) -> {ok, byType, grandTotal, billsOfLading} \| {ok:false, error}` | группировку по типу, поиск колонки коносамента, все уже существующие приватные помощники |
| `grand-total/core.js` | сборку модели данных отчёта из книг | `buildGrandTotalData(workbooks) -> {ok, vessel, voyage, byType, grandTotal, billsOfLading} \| {ok:false, error}` | вызов `buildManifestTotals`/`readVoyageHeader` |
| `grand-total/app.js` | DOM, три поля ручного ввода, сборку и скачивание PDF | — (конечная точка, наружу ничего не отдаёт) | вёрстку PDF через `pdf-lib`, форматирование чисел и типов |

Швы для тестов: `buildGrandTotalData` (новый, основной для этого инструмента), `buildManifestTotals` и `readVoyageHeader` (оба — тестируются отдельно, как уже тестируются соседние функции тех же файлов). Четыре шва, не один — потому что это ровно тот случай из `phases/3-spec.md`, когда несколько требований читают общие данные по-разному (шапка рейса — отдельно от подсчёта весов), и оба уже используются другими инструментами сайта: разделять их пришлось бы всё равно, а `buildGrandTotalData` тестируется дополнительно как единая точка входа именно этого инструмента.

## Вне рамок

Ни одно требование манифеста не откладывается — все десять требований и G01 вошли
в спецификацию (таблица ниже). Отдельно, не как отсрочку чьей-то просьбы, а как
осознанную границу того, что строим — три вещи, о которых никто не просил и о
которых их отсутствие стоит сказать прямо:

| Чего не будет | Почему |
|---|---|
| разбивка по портам внутри этого PDF | эталон показывает только один сводный список по типам контейнеров, без портов — порты уже есть в двух дашбордах сайта, дублировать их здесь незачем |
| предпросмотр PDF перед скачиванием | ни в брифе, ни в эталоне нет упоминания — как и везде на сайте, результат сразу скачивается |
| сохранение введённых вручную позывного/даты/терминала между сессиями | не просили; поля пустые при каждой новой загрузке, как везде на сайте (нет localStorage ни в одном инструменте) |
